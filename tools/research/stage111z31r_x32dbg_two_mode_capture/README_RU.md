# MVKView Stage111Z31R v1.5 — исправление FAdcDataType при уже достигнутом INT3

## Stage111Z31Z — LOG Mode 0: подготовка безопасного одиночного A без B (10.11.2026)

**Исходное состояние:** пользователь открыл первую вкладку Spectrum/LOG оригинальной MVKView, отладчик остановился на EIP `007D14AA` до отрисовки шкалы. Физические 5 bin + JSON независимым Python проверены (Stage111Z31Y); Mode 0 здесь верный. Состояние paused/EIP/PID/TID/EBX/EBP GigaCode после ночи повторно сообщил совпадающим; утверждения о живом процессе основаны на его отчёте, не на прямом доступе этого проекта.

**Не вводить в заблуждение операторский отчёт:**
- `Prepare-Capture.ps1 -SpectrumType 0` генерирует скрипт **A LOG mode0**. В нём `[EBX+08] == 0` проверяется непосредственно; `__ENV_HEX__` для B остаётся `0x14`. Поле `capture_config.json/envelope_code=20` относится **к возможному будущему B**, а не свидетельствует о том, что в текущем A включена огибающая. **Не менять этот параметр вручную на ноль.**
- `Verify-Capture.py` без флагов требует **A+B**, а с новым `--plain-only` выполняет полный физический QA только `A`, включая все `params` с Mode 0, Float32 ring, вход до/после DC, FFT, Power до/после mode, полный Y и 12-байтовую итоговую тройку. Итог `PLAIN_CAPTURE_FILES_VALID_NOT_ORIGINAL_PARITY` **не** доказывает совпадение с BIN/Native или идентичность живого Win32 процесса.
- Генератор требует **все четыре** локальных шаблона `CHECK_READY.template.txt`, `RESUME_A_FROM_14AA.template.txt`, `RESUME_B_FROM_14AA.template.txt`, `ARM_B_ONLY.template.txt` в одной директории с `Prepare-Capture.ps1`. Чтения 5 исходников через GigaCode **недостаточно**, если эти файлы не скачаны на локальный диск. Нужен checkout **всей** папки `tools/research/stage111z31r_x32dbg_two_mode_capture` текущей ветки.
- Сценарии `CHECK_READY.txt`, `RESUME_A_FROM_14AA.txt` создаются **в корне** `Z31R_...`, а бинарные данные — **в подкаталоге** `Z31R_...\A\`. Нельзя запускать `A\RESUME_A_FROM_14AA.txt`: такой путь не существует.

**Подготовка на Windows без изменения состояния отладчика** (из каталога с локально скачанными исходниками):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\Prepare-Capture.ps1" -Adc 4 -N 262144 -SpectrumType 0 -Root "C:\MVK_LOG"
```

Проверить `capture_config.json` (`spectrum_mode=0`, `fft_n=262144`, `adc_claim=4`, `envelope_code=20` — предназначен для будущего B), SHA256 сгенерированного `RESUME_A_FROM_14AA.txt` и отсутствие нераскрытых placeholders. Папка результата выводится генератором; не угадывать её имя. При текущей остановке `EIP=14AA` достаточно подготовленного `RESUME_A`, **никакого ARM_B, B, переключения страницы и F9 вручную**. Сам `RESUME_A` после подтверждения плана **изменяет выполнение процесса** — команды `run` идут до 14B8/153D/154B/17E7/1900; он не является read-only в смысле состояния CPU, только не патчит программу и сохраняет снимки.

**После успешного `Z31R_A_SAVED`**, не возобновляя оригинал:

```powershell
py -3 Verify-Capture.py "C:\MVK_LOG\Z31R_имя_созданного_каталога" --plain-only --report "C:\MVK_LOG\Z31R_имя_созданного_каталога\plain_verification.json"
```

Для первой диагностики можно опустить `--report`: JSON печатается на экран; при заданном `--report` файл должен ещё не существовать. При `Z31R_FAIL_*` сохранять логи/частичные дампы, НЕ повторять `RESUME_A` на неправильном EIP и не нажимать F9. После получения полного исходного `display_y.bin` (N/2 = 131072 Float32 = 524288 bytes) сравнивать с нашим кодом **на том же реальном исходном окне**, не объявлять 1:1 по одному структурному PASS.

## Stage111Z31U — исправление FAdcDataType (v1.5, 09.11.2026)

После успешного `Z31R_B_RESUME` пользователь получил `Z31R_FAIL_STORAGE: invalid storage pointer or FAdcDataType not 1 (float ring)`. Проблема в **нашем ошибочном условии**: исходник `_Unit115.pas`, `TMvkChannelStorage.Create`, адреса `007D0A04..007D0A2F` имеет **0 = Float32**, **2 = byte**, а не `1 = Float32`. Это подтверждает и `007D2228..007D22FD` (отдельная обработка Float32 и byte). Без значения памяти самого пользователя нельзя исключить и ошибочный указатель; поэтому добавлен диагностический лог `Z31R_B_STORAGE_PROBE` и сохранены `mem.base`-guards.

**Текущий сеанс не закрывать**: Paused при EIP `007D14AA`, `[ebx+8]=0x14` (фильтр «1окт 16 кГц»). Для чтения текущего типа без продолжения процесса можно ввести в x32dbg `dword:[ebp-4]`, затем `dword:[dword:[ebp-4]+0x0C]`. Если тип не `00000000` либо указатель недоступен, сначала отправить значения в чат, не обходить ограничение.

В распакованном ZIP v1.5 запустить *только* новый патчер над существующей папкой, из Windows PowerShell (путь первого файла исправить, если распаковка была в другую папку):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\MVK_TOOLS\Z31R_V15\MVK_STAGE111Z31R\Fix-Existing-Storage.ps1" -RunFolder "C:\MVK_CAPTURE\Z31R_20261109_115102_88200486"
```

Патчер проверяет полный SHA256 старого B по `capture_config.json`, схему, код20 и известную старую проверку `==1`. Он не вызывает x32dbg и **не меняет** A, архив, IDP, оригинальный EXE или текущие регистры; сохраняет `RESUME_B_FROM_14AA.v14.bad_datatype.backup.txt`, прошлый B-лог, исправляет точную проверку `==0`, разделяет invalid storage и wrong type, обновляет SHA. Ждать `Z31R_STORAGE_PATCH_OK`. После этого, только если x32dbg остаётся Paused/EIP=14AA/code20, выполнить:

```text
scriptexec "C:\MVK_CAPTURE\Z31R_20261109_115102_88200486\RESUME_B_FROM_14AA.txt"
```

Если снова `Z31R_FAIL_...`, прислать всю строку `Z31R_B_STORAGE_PROBE` и название ошибки. **Не нажимать F9** до понимания причины. Если в дампе будет byte ring type2, этот пакет сознательно отказывается трактовать его как Float32; потребуется отдельный код для правильной реконструкции исходного byte-ring.

Для будущих сеансов Z31R v1.5 сразу генерирует A и B с типом0; проверщик `Verify-Capture.py` принимает только настоящий Float32 type0. Предыдущие тесты v1.4 имели ошибочный синтетический type1 — они не являются доказательством корректности оригинального enum. Новые негативные тесты покрывают 1, 2, 3. Ни один тест CI не запускает оригинальную MVKView/x32dbg.

---

**Это пакет продолжения захвата, а не новая версия самой MVKView.** Спектры, FFT, FRange, FIR, Native Go R6.1 не изменяются. Пакет использует только оригинальную MVKView 1.0.47, открытую в x32dbg, и локальные исходные BIN/TSXML без подключения к прибору. Оригинальные EXE/IDP/PAS/BIN в архив не включены и не отправляются в GitHub.

## История предыдущих ошибок и прежняя v1.4 (не текущая инструкция)

### Что обнаружено на скриншоте пользователя 09.11.2026

- `Z31R_READY_OK`: адреса/инструкции в оригинальной MVKView были распознаны.
- `Breakpoint at 007D14AA set!` и `INT3 breakpoint at mvkview.007D14AA!`: исходный код GetSpectrum был достигнут, это **подтверждённый первый этап**, а не ошибка FRange/FFT.
- `Script is terminated by user.`: прежний единый скрипт был прерван при/после остановки. Скриншот не показывает, произошло это по нажатию пользователя, таймауту сценария или иному событию отладчика. Нельзя утверждать, что исходный GetSpectrum ошибочен.
- После повторного запуска сценария с EIP, всё ещё равным `007D14AA`, правильно сработала защита `Z31R_FAIL_STARTUP`: скрипт запрещал повторно входить в уже выполняемую функцию.
- `Debugger must be paused to run a script!`: дальнейшая попытка запуска произошла тогда, когда отлаживаемый процесс уже выполнялся. **Выполнять scriptexec только в состоянии Paused.**

Почему v1.3: `scriptexec` — блокирующее выполнение; скрипт v1.2 включал `run 007D14AA`, затем ожидал перехода в GUI и второго режима, оставаясь активным. Такой долгий сценарий неудобен при ручном пересчёте и не восстанавливается с уже достигнутого INT3. Новая версия не ждёт пользователя внутри единого скрипта. `run <адрес>` теперь вводится **только в командной строке x32dbg**, когда требуется дойти до первой точки. После остановки работает короткий `RESUME_A_FROM_14AA` или `RESUME_B_FROM_14AA`.

## Если EIP уже 007D14AA и код фильтра 20 (текущая остановка пользователя)

**Найденная ошибка предыдущей v1.3:** исходный `RESUME_B_FROM_14AA.txt` выполнял `bpc 0x007D14AA` без проверки, существует ли breakpoint. После предыдущего неудачного `RESUME_A` breakpoint отсутствовал, поэтому x32dbg прекращал сценарий до первого `savedata`. Это НЕ ошибка исходной FFT/огибающей и НЕ повод менять фильтр.

**Сохранить текущую паузу:** в x32dbg подтвердить `EIP=007D14AA`, `dword:[ebx+8]=00000014` (20d), `Paused`. Никакого F9, `ARM_B_ONLY` и повторного `RESUME_A`.

**Вариант без нового сеанса и без редактирования вручную:** после распаковки пакета v1.4 выполнить Windows PowerShell 5.1:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\MVK_TOOLS\Z31R_V14\Fix-Existing-B.ps1" -RunFolder "C:\MVK_CAPTURE\Z31R_20261109_115102_88200486"
```

Внешний путь к `Fix-Existing-B.ps1` замени на свой фактический каталог распаковки v1.4. `RunFolder` выше основан на твоём фото — проверь его. Исправление не касается самого оригинального процесса, не вызывает `run`/`F9`, сохраняет `RESUME_B_FROM_14AA.v13.backup.txt` и обновляет SHA256 в `capture_config.json`. Ожидается `Z31R_B_PATCH_OK`. Затем, **не меняя текущую паузу**, в x32dbg выполни только:

```text
scriptexec "C:\MVK_CAPTURE\Z31R_20261109_115102_88200486\RESUME_B_FROM_14AA.txt"
```

Если EIP успел измениться, остановись и сообщи новый EIP. Если появится `Z31R_FAIL_*`, не обходи защищающие проверки памяти/окна. Пока A отсутствует, полный `Verify-Capture.py` правильно не выдаст `TWO_CAPTURE` PASS: после успешного B отдельно получим A. `Z31R_BOTH_COMPLETE` в старом тексте B означает только завершение B-скрипта; существование A проверяется отдельно по физическим файлам.

**Для новых запусков:** `Prepare-Capture.cmd` в v1.4 автоматически создаёт B без `bpc` и новый уникальный каталог. Текущую остановку при коде20 не теряй ради создания нового каталога.

## Главное: сохранить достигнутую точку и не повторять всё

Если оригинальная программа **ПРЯМО СЕЙЧАС ещё приостановлена** на EIP `007D14AA` и в ней выбран обычный спектр без фильтра (код0), вы можете **продолжить с этого места**:

1. Распакуйте **v1.4** в локальную ASCII-папку (`C:\MVK_TOOLS\Z31R_V14`) и запустите `Prepare-Capture.cmd`. Программа не трогает оригинальную MVKView, создаёт новую приватную папку `C:\MVK_CAPTURE\Z31R_...` с конфигурацией и готовыми ASCII-скриптами.
2. Убедитесь, что x32dbg показывает `Paused` и **EIP = `007D14AA`**. Не нажимайте F9 и не исполняйте старый `CAPTURE_BOTH`.
3. Откройте `RUN_ME.txt` в созданной папке. Скопируйте **только** готовую команду `scriptexec "...\RESUME_A_FROM_14AA.txt"` в командную строку x32dbg. Скрипт сам выполнит 14AA → 14B8 → 153D → 154B → 17E7 → 1900 и запишет A. Ожидается `Z31R_A_SAVED`.
4. Когда скрипт A завершился и x32dbg приостановлен на `007D1900`, выполните команду `scriptexec "...\ARM_B_ONLY.txt"` из того же `RUN_ME.txt`. Она **только устанавливает** условный breakpoint: код фильтра `[EBX+8] == 0x14` (20 десятичное). Команд `run` и `savedata` в ней нет.
5. После `Z31R_ARM_B_READY` скрипт уже закончен. **Только теперь F9 один раз.** В интерфейсе оригинальной MVKView выберите в меню «Спектр» — **«1окт 16 кГц»** (внутренний код20). Оставьте тот же архив, АЦП4, FFT N, Fs и тип «Линейный ВС». Пересчитайте спектр. Отладчик должен остановиться на `007D14AA` именно при коде20; другие коды условный breakpoint пропускает.
6. Убедитесь, что x32dbg в состоянии **Paused**, EIP = `007D14AA`, `[EBX+8] = 00000014` (шестнадцатеричное число). Теперь выполните `scriptexec "...\RESUME_B_FROM_14AA.txt"`. Ожидается `Z31R_BOTH_COMPLETE`. Скрипт B **не удаляет** breakpoint вслепую — адрес уже достигнут и breakpoint может отсутствовать.
7. Проверьте сохранённое локально: `py -3 Verify-Capture.py "C:\MVK_CAPTURE\Z31R_..." --report "C:\MVK_CAPTURE\Z31R_...\verification.json"`. Отправьте в чат ZIP созданной папки, не в публичный GitHub.

Если текущая пауза **уже потеряна** (EIP не 14AA), используйте свой оригинальный архив №83/АЦП4: при Paused в x32dbg введите `run 0x007D14AA` **в командную строку, не как scriptexec**, дождитесь запуска GUI, пересчитайте обычный спектр и затем выполняйте шаг 3. Повторять всё исследование FFT/FRange не нужно.

## Контрольные точки и файлы

| Момент оригинального GetSpectrum | Выходные данные |
|---|---|
| `007D14AA` | FRange, Storage (56 байт), до DC и исходная кольцевая история (в т.ч. wrap) |
| `007D14B8` | вход после DC |
| `007D153D` | после FIR (для B) или без FIR (A), перед FFT |
| `007D154B` | Power FFT до режима |
| `007D17E7` | Power после режима и **весь массив Y** |
| `007D1900` | Params, итоговая тройка Float32 |

В `A` и `B`: `params_*.bin`, `input_normalized_pre_dc.bin`, `input_after_dc.bin`, `before_fft.bin`, `power_before_mode.bin`, `power_after_mode.bin`, `display_y.bin`, `storage.bin`, `frange.bin`, `ring_head.bin`, при необходимости `ring_tail.bin`, `summary_triplet.bin`. Отдельные логи: `capture_a.log`, `capture_b.log`, `capture_log_a_snapshot.txt` и `capture_log_b_snapshot.txt`. Верификатор требует точных размеров и согласованных Params. Даже если эти два набора физически правильны, **привязка к исходному BIN и полное совпадение с нашим алгоритмом остаются отдельной проверкой**.

## Какие сбои запрещено обходить

- **`Z31R_FAIL_RESUME_ENTRY`**: EIP не 14AA; не пытайтесь повторно запустить из другой инструкции.
- **`Z31R_FAIL_FILTER`**: выбран неверный код. Для A ожидается 0, для B 20 (`0x14`).
- **`Z31R_FAIL_MEMORY`**, **`Z31R_FAIL_HISTORY`**: память или исходные отсчёты не соответствуют безопасным условиям; не выключайте проверки.
- **`Z31R_FAIL_FRAME`**, **`Z31R_FAIL_STOP`**: нельзя утверждать, что последовательные буферы относятся к одному вызову.
- **`Script is terminated by user`**: не запускайте старую монолитную программу ещё раз; сохраните лог, физический EIP и параметры регистров, не нажимайте F9 через неясную остановку.
- **`Debugger must be paused to run a script!`**: дождитесь действительной паузы x32dbg; только тогда `scriptexec`.

## Доказательные ограничения

Процесс оригинальной MVKView из ChatGPT не запускается. **Linux синтетические тесты и Windows PowerShell 5.1 smoke не могут доказать, что x32dbg выполнит каждый `run` в оригинале**. Это должен подтвердить первый операторский запуск. Коды фильтров и output Fs сохранены прежние: код0 без FIR, код20 «1окт 16 кГц» с итоговой выходной частотой 32768 Гц. Скрипт не меняет вычислительные данные и файл оригинального EXE; обычные программные точки останова x32dbg временно используют INT3 в памяти отлаживаемого процесса. Подключения к реальному прибору нет.
