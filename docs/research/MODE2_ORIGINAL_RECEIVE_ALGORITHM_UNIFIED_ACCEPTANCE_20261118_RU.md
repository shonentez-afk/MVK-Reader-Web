## Оригинальный алгоритм получения данных, который должен проходить сквозную приёмку

1. **IP и кнопка.** Оригинал загружает \`Device/Address\` из конфигурационного XML (резерв \`192.168.0.30\`); текущее \`edIpAddr\` передаётся в конструктор потока. \`bTaskConnectClick\` выбирает Mode2, меняет видимость исходных страниц и запускает один \`TMVKThread\`. Видимые вкладки сами по себе **не означают** успешного TCP.
2. **Транспорт и состояние.** Исходный \`TIdTCPClient\` подключается к IP прибора через TCP/10230: ConnectTimeout 1000 мс, ReadTimeout 5000 мс. На новом сокете Task2 начинается со Stage0. Первый **непустой корректный PARAM** переводит его в Stage1; настоящий системный статус \`StatusCells[0]>0\` — Stage3. Неизвестный/ещё не полученный статус не заменять нулём.
3. **Исходящий SetRate.** \`mRate1Click(Items[0])\` выбирает по умолчанию 65536 Гц, \`TMVKThread.SetRate\` сначала обновляет \`MvkSampleRate\`, затем ставит команду в FIFO. В Stage1 перед следующим чтением поток извлекает **не более одной** команды. Команда SetRate — 36 байт на **том же сокете**. ACK не содержит идентификатора транзакции, DENIED инициирует исключение/повторную попытку. В совместимом клиенте физическую TX и дальнейший reconnect разрешать **отдельно**; пассивный режим остаётся возможным. Flash/IP/Reboot не отправлять автоматически.
4. **Реассамблирование.** TCP даёт непрерывные байты, а не сообщения; приёмник собирает кадры независимо от размера \`Read\`. Заголовок — \`type:u32le\` и \`length:u32le\` (длина **включает** 8 байт заголовка); исходный допуск \`8 ≤ length ≤ 0x20000\` и \`length % 4 == 0\`. Для ADC/TACH требуется не менее 28 байт, для PARAM не менее 32, для ACK/DENIED — 8. Известные IDENTITY/PARAM/ADC/TACH/ACK/DENIED обрабатываются; корректно оформленный неизвестный тип **пропускается по его длине**, не руша следующую синхронизацию. Некорректная длина/дескриптор — недостоверный кадр, не «нулевые» измерения.
5. **Отсчёты ADC/TACH.** Типы \`ADC=0xFF800ADC\`, \`TACH=0xFF8001AC\`. После 8-байтного заголовка ещё пять \`u32le\`: индекс отсчёта находится по смещению 12, индекс канала — 20, частота Fs — 24; далее со смещения 28 идут 4-байтные слова. ADC0..7 — исходные Float32, TACH8..9 — **сырые байты** (\`4 × количество слов\`), не переводить их в Float32 при хранении оригинального тахоканала. Пакет без отсчётов не увеличивает счётчики. Фиксировать разрывы индексов, Fs и статус 10 каналов.
6. **Два независимых слоя данных.** \`incoming.raw\` сохраняет **все** принятые байты, включая неподходящую Fs, Freeze и неизвестные кадры. Только для исходного кольца/WriteData действует условие \`received Fs == MvkSampleRate && FreezeUpdate == false\`. Исходный кольцевой буфер — \`2^21\` элементов **на канал**; для ADC элемент Float32, для TACH элемент Byte. Изменение Fs, разрыв индекса или несовместимая область калибровки не могут незаметно сохранять непрерывность. Формулу исходного gain/FRange и \`GetSignal\` для конкретного окна ещё требуется принять отдельно.
7. **PARAM и приборные величины.** \`PARAM=0xFF800C0D\` несёт проверяемые дескрипторы адреса/числа 16-битных слов; они обновляют register image. Архивный кадр AUX4700 содержит 8 блоков приборных данных и третьоктавные значения. **Только реально полученный дескриптор \`0x3100\`** запускает исходный \`WriteValues\` при открытом writer-е; сам AUX4700 не является этим триггером. Формат окончательных Delphi CSV зависит от \`TMvkCellList.GetValueText 007CF4A4\`, включая advanced titles.
8. **Параллельные писатели и визуализация.** \`WriteData\` открывается по операторскому действию и переключает Stage0→1 **только при первом допустимом ADC1**; затем сохраняет выбранные реальные ADC/TACH bytes, не вычисленный FFT. \`WriteValues\` фиксирует выбор SPEC/VALUES и события \`0x3100\` отдельно. Freeze запрещает обновление оригинального кольца, **но не остановку получения RAW**. Обновление UI/курсора/спектра — отдельная downstream-ветка после принятия сигнала, не доказательство исходного вычисления \`GetSpectrum\`. Qt применяет операторские маркеры к границе следующего **декодированного** кадра, что пока не равно точному Win32 microtiming оригинала.
9. **Stop и отказ.** Отмена потока / ошибка должны закрыть файлы, зафиксировать истинную причину завершения, контрольные суммы RAW и результат каждого writer-а; неполный/битый канал **не объявлять успешным**. На reconnect — новый TCP, Stage0 и отдельный SHA для его сегмента; нельзя выдавать конкатенацию разных сокетов за единый original run. Итоговый Python Core независимо перечитывает Go журналы и \`incoming.raw\`, а GUI показывает проверенные значения, без фиктивных DSP/спектров.

### Что должно считаться PASS в CI

Одна сборка **точно на финальном SHA**, Linux Go RX/export (включая loopback с действительным 36-byte SetRate), Linux Python Core, Windows Python Core+Qt, Windows DPI100/150 QPA, затем Windows EXE — все пять jobs \`success\`. Новый Go тест подаёт реассамблированные фрагменты всех 10 каналов, проверяет неизвестный тип, пустой ADC, wrong-Fs, Freeze, RAW/SHA, разделение ADC и TACH, независимый \`0x3100\` и закрытие writer-ов; отрицательный тест запрещает превращение повреждённого заголовка в измеренный ADC. Приватные исходники никогда не запускаются в CI.

### Что необходимо для окончательного **аппаратного** PASS

При разрешении оператора: (1) один контролируемый полный цикл на реальном МВК01 через выбранный Ethernet, с отдельным подтверждением любого SetRate, коротким ограничением RAW и независимым Wireshark; (2) корректное поведение кнопок во время записи, выбор ADC/TACH и VALUES, Freeze, изменённая Fs, Stop; (3) отказные сценарии timeout/DENIED/reconnect с отдельным разрешением и сохранением неполного RAW; (4) независимая сверка PCAP ↔ \`incoming.raw\` ↔ десяти каналов ↔ Go writer ↔ Python Core ↔ отображения; (5) оригинальные Delphi \`GetSignal/GetSpectrum\`, BIN/TSXML/CSV и Win32 timestamps — проверять **на тех же исходных данных**. Два независимых измерения в разное время **не являются** доказательством побайтовой 1:1 совместимости.

**Итоговое условие:** \`original_delphi_compatibility_verified\` остаётся \`false\` до аппаратной проверки и независимой парной сверки оригинала. Успешный CI = принят синтетический сквозной контракт, **не** завершено восстановление оригинала.
