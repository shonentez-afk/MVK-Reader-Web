# Stage 49 — проверка FRange в спектральном тракте MVKView

2026-10-28. Источник: экспорт IDR _Unit115.pas / _Unit125.pas, пять реальных BIN и четыре TSXML. Stable v0.3.40 не изменена.

## Подтверждено по IDR
- 0x007D0A61: начальный FRange = 1.0 (не означает фактический коэффициент при записи).
- 0x00808284 / 0x0080828C: приёмный TCP-путь вызывает ProcessBufferChunk с ApplyRange=True.
- 0x007D23D5: в ветви FAdcDataType=0 (float32) ProcessBufferChunk умножает значения рабочего буфера на FRange.
- 0x007D149A / 0x007D22C8: GetSpectrum читает float32-буфер с флагом 1 и делит на FRange.
- 0x007D1667, 0x007D16F1, 0x007D17B0: линейные спектральные режимы умножают выходную амплитуду на FRange.
- 0x007D2321: ветвь FAdcDataType=2 интерпретирует byte/255; к ней нельзя без проверки переносить правила float32.

Таким образом, на стандартном float32-пути при ненулевом FRange: `x -> x*FRange (буфер) -> /FRange (FFT) -> amplitude*FRange`. Это не двойное усиление; физический масштаб возвращается на выходе.

## Проверка данных
Статические проверки: 8/8. Прочитано пять BIN как float32 LE, подмножества 65536 отсчётов проверены на численную обратимость выбранных множителей. TSXML InternalChannelGain: 510.6 (№83 ADC1), 509.7 (№83 ADC3), 509.6 (№83 ADC6), 509.9 (№84 ADC4). Это **не доказанный FRange**. Численные RMS по отдельным BIN и ошибки округления — в локальном `RESULTS.json`.

## Открыто
Нужно найти путь записи BIN (до/после ProcessBufferChunk) и конфигурационный источник FRange. Не выдавать InternalChannelGain за FRange, не объявлять совпадение оригинального спектра по одному только статическому тесту. Следующий Stage 50: BIN/TSXML writer и источник коэффициента.
