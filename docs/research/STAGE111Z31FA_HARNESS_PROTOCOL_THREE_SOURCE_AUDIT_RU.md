# Stage111Z31FA — исправление протокольного отчёта DeepSeek Harness по оригинальному MVKView

**Дата:** 17.11.2026. Исследовательская ветка `research/stage111-mvkview-desktop-20261029`.

**Итог:** пользовательские `MVK_PROTOCOL_AND_CHAIN_RECOVERY.md`, `MVK_PROTOCOL_EVIDENCE.json` и `MVK_PROTOCOL_CHANGES_AND_TESTS.md` полезны как перечень исходных инструкций, но содержат 10 расхождений с оригинальным листингом и один пробел источников. **Не переносить** предложенные `spec/dto/*.py` непосредственно в Core: там уже есть более полная и корректная проверяемая реализация.

## 1. Три источника использованы совместно

1. `mvkview.idp`: локальный файл проверен по SHA256 и размеру относительно поля `meta.idp_header` оригинального SQLite-индекса; метаданные IDR project v3, image base `00400000`. Полная внутренняя база IDP **не декодирована**; не выдавать метаданные за анализ всех RTTI и типов.
2. `Projects.7z`: открыт **напрямую** в режиме только чтения через libarchive (7z, без копирования в публичный репозиторий). Для `_Unit115.pas`, `_Unit116.pas`, `_Unit123.pas`, `_Unit125.pas`, `_Unit128.pas`, `mvkform.dfm` размер и SHA256 содержащихся в архиве байт совпали с записью в `mvk_idr(1).sqlite/source_files`. Важная проверка: 6 из 6 соответствий.
3. `mvk_idr(1).sqlite`: открыт `mode=ro` с функциями/вызовами/событиями и адресной картой. Его индексация связывает машинный листинг и DFM; это самостоятельный индекс, а не полная расшифровка всех внутренних объектов IDP.

Три оригинальных файла, исходный EXE, исходные BIN, изображения и частные пути в GitHub не добавляются. Факты ниже — только производная краткая карта.

## 2. Настоящая таблица входящих типов

| ID кадра | Тракт оригинального Execute | Что ошибочно написал Harness | Нынешний Core |
|---|---|---|---|
| `0x00000001` | `00808060–00808076`: читает и **отбрасывает** оставшиеся UInt32; **не** создаёт измерения | `DATA_STREAM` | `TYPE_IDENTITY` → `IDENTITY_DRAIN`; название identity — ярлык модели, факт — слив слов |
| `0x00010FF0` | `0080807B`: логирует **успешное выполнение операции**; без доказанного сопоставления с нашей SetRate | `STATUS_CONFIG` | `TYPE_ACK` → `ACK_OBSERVED` |
| `0x00010FFF` | `008080AC`: исключение `errOperationDenied` | `DEVICE_ERROR` | `TYPE_DENIED` |
| `0xFF8001AC` | `008080EB`: общий обработчик исходных выборок, источник тахометрических данных по восстановленной карте каналов | `REPLY_A` | `TYPE_TACHDATA` |
| `0xFF800ADC` | `008080EB`: общий обработчик исходных выборок, источник АЦП по восстановленной карте каналов | `REPLY_B` | `TYPE_ADCDATA` |
| `0xFF800C0D` | `0080839E`: блоки PARAM/регистров, 5 слов заголовка, количество блоков, дескриптор `(wordCount << 16) | address`; управление исходными `Stage` | `REPLY_CMD` (просто ответ команды) | `TYPE_REGISTERS` |

Наличие одинакового `0xFF800C0D` у исходящей команды и входящей PARAM-ветки **не** доказывает, что любой такой входящий кадр является ACK непосредственно нашей команде. Строка `00808060` **не** содержит вызова `ProcessBufferChunk`. Реальный `ProcessBufferChunk` находится ниже, в `0080828C`, в обработчике `0xFF8001AC/0xFF800ADC`, после проверки выбранной частоты и `FreezeUpdate`.

Статическая проверка общего заголовка подтверждается `00807F78/84` (два `TIdIOHandler.ReadUInt32`), проверками `00807F8D..00807F9F` (`8 <= length <= 0x20000`, длина кратна 4), расчётом `(length-8)/4` на `00808019..0080801C`. Порядок байт для вызовов Indy с `AConvert=False` источниковедчески прослеживается через `007F3E58` и `007D8968`; физический захват любого пакета пользователя в этой конкретной проверке не выполнялся.

## 3. Исходящая команда: 8 слов + 1, а не фиксированные 9 внутри `0080937C`

| Где | Что доказано |
|---|---|
| `00809330` | `QueueCommand(Cmd: Integer, Addr: Cardinal, Data: Cardinal)` выделяет 12 байт **в памяти** (`Cmd`,`Addr`,`Data`) и добавляет запись в `TList` |
| `00809364` | `QueueCommand(Cmd=1, Addr=0x0E, Data=MvkSampleRate)`; **0x0E — Addr, не Cmd**, 1 — Cmd |
| `00809400` | `SetRate` не ставит вторую команду, если код уже совпадает |
| `00807E9F..00807F40` | В `Stage=1` поток выбирает одну запись из очереди; передаёт `Addr` как EDX, фиксированный ECX=2 в `0080937C` |
| `0080937C..008093FD` | **Ровно 8** вызовов `TIdIOHandler.Write`: `0xFF800C0D`, длина, четыре нулевых DWORD, `1`, `(2<<16)|Addr` |
| `00807F45..00807F52` | **Девятый** вызов `Write(Data)` находится в `TMVKThread.Execute`, **не в `0080937C`** |

Для SetRate с `Addr=0x0E, Data=65536`: восемь слов заголовка `(0xFF800C0D,36,0,0,0,0,1,0x0002000E)` плюс одно слово `65536`; общий исходный поток Write-аргументов — **36 байт**. Для абстрактного вызова только `0080937C` с `ECX=0` указанная в нём длина равна **32** байтам и функция выдаёт **32** байта; отчётный `build_wire_command(arg1, arg2)` неверно выдаёт 36 байт при любом `arg1`. Его синтетические тесты при этом не проверяют соответствие общей длины фактическому числу выдаваемых байт. Строить на этой функции аппаратный передатчик нельзя.

В GitHub эта структура **уже реализована безопасно, без открытия сокета**, в `mvk_compatible/core/original_mode2_wire_word_candidate.py` и `original_mode2_command_queue.py`; `original_mode2_task2_exchange.py` раздельно моделирует постановку команды и исходное получение PARAM-кадров. Existing Stage111Z31DD/DH tests проверяют 8+1 вызовов и 36 байт.

## 4. Другие ошибки отчёта

- `TMVKThread.WriteDataTime` находится на `+0x404E0` (запись `008061B2`, `0084E936`), а не на `+0x400E0`. `WriteValuesTime` — `+0x404E8` (`008061BF`, `0084E9B3`). В этих местах оригинальный листинг точнее декомпилятора.
- `Tmvkform.tmInterfaceUpdateTimer` начинается с `0084F7C8`: **`call 00847248; ret`** (`0084F7CD`). Большой обработчик с обращениями к `+0xBD8` и `+0x21124` — **другая** функция `sub_0084F7D0`.
- В отчёте `Projects.7z` **не анализировался**; метаданные IDP прочитаны через SQLite, а не из внутренних IDP-объектов. Поэтому заявление о полном независимом трёхстороннем исследовании нельзя принимать за подтверждённое самим Harness. Здесь архив проверен самостоятельно.
- Кнопка `bTaskViewClick` (`00848E84`) выбирает офлайн-просмотр, не остановку живого измерения. Само `Измерение` (`00848E78`) выбирает Mode2; повторное нажатие этого обработчика при Mode2 идёт через сброс `00847040`.
- В комплекте `MVK_PROTOCOL_CHANGES_AND_TESTS.md` описан проект тестов, но **нет фактически изменённых модулей или результата выполнения этих тестов**. Названия `spec/dto` в том документе — предложения, не существующая реализация.

## 5. Состояние текущего Core/Qt и безопасность

В ветке `research/stage111-mvkview-desktop-20261029` уже присутствуют:

- `original_mode2_received_frames.py`: ограниченный непрерывный приёмный фреймер и корректный диспетчер всех шести типов (модель **только чтения**, без сокета).
- `original_mode2_wire_word_candidate.py`: 8 заголовочных Write + 1 Data и исходные LE-байты как **пассивное доказательство**, без операционного TX.
- `original_mode2_command_queue.py`, `original_mode2_task2_exchange.py`: очередь `Cmd/Addr/Data`, SetRate и исходные стадии/ошибки без устройства.
- Тесты `test_stage111z31dd_source_wire_word_candidate.py`, `test_stage111z31dg_source_received_frames_core.py`, `test_stage111z31dh_source_task2_exchange_core.py` и Qt-тесты приёма.
- Отдельная контролируемая **opt-in** возможность отправки **только** разрешённого оператором `SetRate` через единственный Go TCP-клиент, с проверкой происхождения TX в `original_mode2_active_tx_provenance.py`. Наличие кода TX **не** равно факту отправки в этой сессии и не разрешает произвольные команды, прошивку, Upload/Calib и т.д. Нельзя автоматически включать запись из-за нового отчёта Harness.

**Решение:** не переписывать имеющиеся Core/Qt-модули из упрощённого внешнего предложения. Добавить независимую CLI-сверку отчётов и специальные регрессионные тесты, чтобы ложная классификация кадров и неверные 9 заголовочных слов не попали в последующие PR. Прямой численный и аппаратный паритет продолжает требовать отдельной приёмки.

## 6. Реально выполненные проверки

- Из 3 оригинальных файлов SQLite в `mode=ro`; внутренний IDP-вход метаданных/длина/контрольная сумма совпали; `Projects.7z` прочитан напрямую и шесть выбранных PAS/DFM совпали по байтам с индексом.
- `tools/research/reconcile_harness_protocol_evidence.py` на пользовательском JSON: **10 расхождений по источнику + 1 пробел происхождения**. JSON с машинным списком замечаний без приватного содержимого сохранён отдельно.
- `tools/research/tests/test_reconcile_harness_protocol_evidence.py`: **5/5 PASS** локально. Проверены валидная карта, ошибочные ярлыки, 9 фиксированных слов, смещение времени и таймер, отказ при дубликатах/пропущенных типах.
- `mvk_compatible/tests/test_stage111z31fa_harness_protocol_source_regressions.py`: добавлены **4 теста**, которые необходимо выполнить в CI существующего проекта; внутри этой локальной среды импорт всего Core не выполнялся. Не утверждать PASS до отчёта CI.
- Основной исходный Core/Qt **не изменён**: исследование не обнаружило новой достоверной спецификации, которая требует исправления ядра, и внесение неподтверждённых изменений ухудшило бы приложение.

## 7. Следующий крупный блок

Дальнейшее исследование должно восстановить именно **неизвестное**, используя три локальных источника совместно и сверку с уже существующим Core+Qt:

1. `0080816B–00808399`: реальная раскладка пяти слов заголовка ADC/TACH, каналов 0..9, прерывистого `ReadStream`, `ProcessBufferChunk`, `FreezeUpdate`, `WriteDataStage`, параметры `FRange` и численная калибровка.
2. `0080841B–008087BB`: полные дескрипторы PARAM `0xFF800C0D`, адреса регистров, Stage0→1, `StatusCells`, триггер `0x3100` для исходных CSV; не отождествлять с AUX4700.
3. `00807D00–00807F68`, `00809288–00809414`: условия выталкивания очереди и 8+1 слов; независимая проверка байтов исходных команд в уже доступных **офлайн** данных, без нового аппаратного TX.
4. Сквозной Core + Qt + native Go тест **одной** подтверждённой записи, отдельно численный и GUI паритет; не объявлять поддержку всех окон/кнопок до проверки.

Ни один исследовательский вывод не требует запуска оригинального прибора в ходе этого аудита.
