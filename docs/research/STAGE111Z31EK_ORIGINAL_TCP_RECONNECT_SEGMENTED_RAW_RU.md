## 1. Оригинальное поведение: подтверждено по Projects.7z

В локальном, непубликуемом архиве Projects.7z / Projects/_Unit125.pas (CP1251) повторно найдены следующие точные участки:

- `00807BC2–00807C39`: начало повторяемого блока TMVKThread.Execute. При новом цикле Stage=0, создаётся новый TIdTCPClient, IP из TMVKThread.IPAddress, порт 10230, ConnectTimeout=1000 мс, ReadTimeout=5000 мс.
- `00808871–0080899B`: исходные ветки исключений EIdConnClosedGracefully, EIdReadTimeout, EIdConnectTimeout, EIdException, с освобождением старого TCP-клиента.
- `008089A3–00808B15`: после завершения соединения при Task=2 Stage=0; отображается ожидание, потом при not FTerminated условный переход обратно на 00807BC2 — **повторное подключение также после активного измерения**, не только до первых RAW-байтов.
- `008061C6`: constructor PauseValue:Single=25.0, `00808AAF–00808ADA`: задержка `(Round(PauseValue)+1) × 10 мс`; `00808ADA–00808B0E`: плавное умножение на √2 при исходном пороге 801. Точный начальный ряд 260, 360, 510, 720 мс, далее до 8020 мс (обновлено относительно старого приближения 250,350,500,710 мс).
- `00807E8F–00807F52`: FIFO исходящей оригинальной SetRate только после реального PARAM/Stage1. Новая TCP-сессия не должна использовать status0=0 из предыдущей физической сессии.

**Исходные файлы _Unit125.pas, IDP, SQLite и пользовательские PCAP/RAW не загружались в публичный GitHub.** Документ содержит лишь адреса, короткое описание и независимую программную модель.

## 2. Единое Go-ядро: одна физическая сессия — один источник RAW

Новые модули:

- `source/source_tcp_segments.go`: `sourceTCPLedger`, на каждом TCP Connect/Disconnect записывает UTC, начало/конец диапазона в неизменном общем `incoming.raw`, причину отключения, незавершённый хвост пакета, число фактически переданных байт команд. При новом Connect сбрасывает **Framer.Tail, весь RegisterImage.Valid и DSP, Stage0/Status0 источника**, а также признаки непрерывности счётчиков ADC/TACH. При завершении из исходного RAW потоково извлекаются отдельные `SOURCE_TCP_SEGMENT_0001.raw`, `...0002.raw` и т.д., вычисляется SHA256 каждого сегмента и `SOURCE_TASK2_TCP_SEGMENTS.json`. Все копии проверяются по непрерывным независимым диапазонам; manifest SHA256 включён в исходный Go `summary.json`. Ничего не копируется из другой сети и не соединяется без явного журнала.
- `source/source_task2_connect_retry.go`: source-проверенные 1000/5000 мс и точный backoff; `sourceTask2CaptureAddressRetry` может повторить попытку **после уже принятого RAW**, но только с отдельным разрешением. Используется тот же выбранный локальный Ethernet/NIC и исходный IP. После новой сессии разрешённая `SetRate` ставится в FIFO и отправляется **только после нового PARAM и заново подтверждённого `0x1006=0`**.
- `source/main.go`: единственный операторский scanner/QProcess stdin на ВСЕ повторные подключения; переустановка command writer `conn` происходит **ПОСЛЕ** сброса Stage0, чтобы новая SetRate не потерялась. Нет второго Qt TCP клиента.
- `source/monitor.go`: счётчики сессий, reconnectAfterRAW, orphaned tails, независимые RAW hashes, real TX. Сеансы в одном диагностическом `incoming.raw` не объявляются непрерывным сигналом; `session_export.go` отвергает единый проверенный BIN/TSXML, когда принято больше одного TCP-сокета. Сохранение всех исходных байтов при этом продолжается.

## 3. Разрешения, Qt и независимая проверка

- Go принимает два новых флага только с независимым согласованием: `-source-task2-reconnect=true`, `-source-task2-reconnect-approved=true`. Дополнительно обязательны существующие `-approve=true`, `-source-setrate-tx=true`, `-source-setrate-tx-approved=true`, `-live-status=true` и `-stop-file`. **По умолчанию всё выключено**. Flash/reboot и произвольные команды запрещены.
- Python `CaptureSpec.source_auto_reconnect` и Qt чекбокс `r6OriginalTask2ReconnectAfterRAW`: отдельное разрешение, автоматически не включается и сбрасывается при снятии source SetRate разрешения. Обычное измерение без флага не меняется.
- `core/source_tcp_segments.py`: после завершения ищет одну Go-сессию, сверяет SHA исходного RAW, манифеста, каждого `SOURCE_TCP_SEGMENT_NNNN.raw`, непрерывные диапазоны и Go `summary.json`. Проверка потоковая с ограничением памяти; подменённый или неполный сегмент отвергается.
- Если единый BIN отклонён из-за многосокетного потока, Qt **не выдаёт ложный архив**; штатная кнопка «Открыть результат» открывает проверенную локальную папку с раздельными RAW, JSON и SHA. Старые графики предыдущей TCP-сессии скрываются.
- `core/native_r6_live_status.py`: проверяет атомарные поля `source_tcp_connection_count`, `source_tcp_multi_socket`, `source_tcp_reconnects_after_raw`; повышает качество предупреждения. `core/original_mode2_runtime_trace.py`: при новом сокете очищает старый source system error Stage3 и 14 StatusCells, показывает CONNECTING и сохраняет монотонные итоговые счётчики.
- CI: Go localhost fake MVK — два ПОСЛЕДОВАТЕЛЬНЫХ настоящих TCP-сокета, проверка 36 байт SetRate на каждом; отдельные RAW manifest и отказ слить BIN; Python проверки SHA/подмен/согласий, Qt DPI100/150 тест смены реального соединения и сброса старой Stage3.

## 4. Чего ещё нет и что НЕ объявлять восстановленным

1. Byte-identical Windows MVKView 1.0.47 для BIN, TSXML, WriteData/WriteValues при смене Fs или после reconnect: отдельные TCP RAW уже сохранены, но объединённый BIN **не принимается**. Нужен независимый сегментный writer/extraction и численная сверка на одном оригинальном сеансе.
2. Физическая аппаратная проверка повторных SetRate, корректного ACK конкретной команды (неизвестный transaction ID), stream sensitivity, DSP/FFT/RPM/TQGrapher, 15 форматтеров PageStatus — без оригинального работающего стенда не считать готовым.
3. Пока explicit consent на пост-RAW reconnect сохраняет отличия от автоматического поведения Delphi. Это осознанный промышленный барьер допуска, не отсутствие кода повторного соединения.
4. Объединять разные TCP-сокеты в один сертифицированный BIN/TSXML запрещено. Raw-only архивы с manifest не следует передавать как готовые данные калиброванной измерительной программы.

Следующий этап: безопасное воспроизведение original file-writer по каждой отдельной TCP-сессии, после source-проверки структуры, и сквозная проверка обеих партий на одном синтетическом/реальном наборе без искусственного непрерывного Fs.
