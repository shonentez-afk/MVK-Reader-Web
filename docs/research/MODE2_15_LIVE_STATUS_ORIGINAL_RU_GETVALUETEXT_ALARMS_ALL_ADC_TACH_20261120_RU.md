## Главная обнаруженная ошибка и точное исходное поведение

Раньше у live-страницы **Контроль** для одного DWORD `+0x132` выводились **две одинаковые RAW строки** — «состояние» и «событие». Это не поведение исходного `TMvkCellList`.

`_Unit125.pas:00805241..0080528E` создаёт `AlarmState` с **Bits=8, BitStart=0, UseCompositeTitle=false**. `_Unit125.pas:00805293..008052E0` создаёт `AlarmAlert` с **Bits=8, BitStart=8, UseCompositeTitle=true**. Это **один и тот же** полный DWORD `+0x132`, обновлённый валидным исходным PARAM. `_Unit115.pas:007D0808` для State делает точный поиск ID либо `(0xXXXXXXXX)`, для Alert выбирает все ID, удовлетворяющие `(entry_id & value)==entry_id`, и объединяет их через `; `, при отсутствии — `---`.

Теперь источник отображает три исходные ячейки каждого из восьми контрольных мест/каналов: `AlarmValue` Float32 (полный `+0x130` DWORD), `AlarmState` (низкие 8 бит `+0x132`) и `AlarmAlert` (вторые 8 бит `+0x132`), с русскими оригинальными названиями. Неполный/отсутствующий DWORD остаётся **«—»**, включая непринятый второй АЦП, а не «ОК». Пример только **синтетического** регистра `0x00000511`: state ID=17 → «Зеленая зона», Alert bits=5 → «Ошибка датчика (Устар. ПО); Переход в желтую зону». Не считать вычисленные состояния реальным измерением.

`_Unit125:008053B8..00805510` подтверждает TACH6: два Float32 в Гц (`+0x00/+0x02`) и четыре UInt32 (`+0x04/+0x06/+0x08/+0xFE`). Последнее `+0xFE` остаётся UNKNOWN без независимого подтверждения свежести. Никакого выдуманного RPM.
