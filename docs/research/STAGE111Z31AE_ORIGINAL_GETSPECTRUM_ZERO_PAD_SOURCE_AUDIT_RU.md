# Stage111Z31AE — original 007D2228 ZERO-PAD at live code20/LOG14AA; reject unsafe GigaCode ZIP (10.11.2026)

## Главный source-derived результат — НЕ нужно объявлять повторный запуск обязательным

После независимого аудита **оригинального PRIVATE** `Projects.7z/Projects/_Unit115.pas` установлен порядок:
- `TMvkChannelStorage.GetSpectrum` вызывает `CheckDataAvailability` по базовым параметрам в `007D1426` **ДО** `GetAdjustedEnvelopeLength` в `007D146A` и до копирования сырого входа;
- `007D14A5 call 007D2228` готовит full raw Float32 и возвращает **ДО текущего EIP=007D14AA**;
- `007D2238..2265` сравнивают `rawN` c `FRxPos-FValidPos`; если вход длиннее реально доступной истории, то `missing=rawN-(FRxPos-FValidPos)`;
- `007D2275..2284` используют `FillChar`, выставляя **ровно missing * 4 первых байт рабочего буфера в ноль**;
- `007D2291..22D9` читают оставшиеся Float32 из ring по mask и делят их на `FRange`. Далее `007D14B3` удаляет DC, `007D14E9` выполняет I/Q, `007D1546` FFT.

Поэтому исходный Delphi код **обрабатывает неполную исходную историю с ZERO-PAD**, а наше прежнее правило x32dbg `start>=oldest` в v1.5 `RESUME_B` — **слишком строгое для воспроизведения фактического оригинала**. Не путать `Z31R_FAIL_HISTORY` от **нашего** инструмента и исключение самой MVKView. Фактический массив на текущей 14AA после copy ещё требуется снять/проверить, но код однозначно свидетельствует о допустимой исходной логике заполнения. Запрет автоматического F9/переустановки BP сохраняется.

### Применение к текущей operator-reported паузе

Со слов GigaCode: `EIP=007D14AA`, Mode0/EnvelopeCode20, `rawN=262195`, `WindowEnd=524339`, `FValidPos=294912`, source Fs65536, FRange0x43FF4853, type0. **Требуется read-only подтвердить `FRxPos=[Storage+0x20]`, high `+0x24`, valid high `+0x2C`, `byte:[EBX+14]`.** Если `FRxPos=WindowEnd=524339` с нулевыми старшими словами, то `available=229427`, `missing=32768`. После helper `[EBP-0x2C]` должен указывать на **уже готовый рабочий Float32** `rawN*4=1048780 bytes`, его первые `32768*4=131072 bytes` должны быть **в точности нулевыми**, а оставшиеся 229427 Float32 — действительным нормализованным входом. Нужен runtime dump и SHA; соответствие raw suffix с физическим ADC1 BIN проверять **по реальным байтам**, не переносить на B индексную карту от LOG A без проверки.

По source `007D1E70: (input_n - taps)//decim`, для stage5 taps51 / decim2 ожидается `FFT N=131072`, `Power/Y 65536 Float32`; подтверждение надо снимать **на EIP153D**, не на EIP14AA. Перед этим не продолжать процесс без отдельного согласия оператора. `[Storage+0x10]=0x00200000=2097152` отсчётов, `mask=0x001FFFFF`; ошибочное число 8192 опровергается raw bytes. Заявленная GigaCode region `[0x07BB0000,0x07CF0000)` **не содержит** ring pointer `0x7E620010`, поэтому это не проверка физической страницы буфера.

## Аудит полученного пакета GigaCode `MVK_STAGE111Z31AD_PACKAGE.zip`

Аудит завершён локально (7 файлов, ZIP читается). **Ни один из его x32dbg-скриптов не запускать.**
1. `verify_b.py`: CLI падает с `AttributeError: BValidator.expected_Fs_output`. Прямой тест класса на 4 Float32 возвращает **`verdict=PASS` при `rawN_match=False`** — недостоверная приёмка. `--plain-only` фактически не меняет путь; `--fftN` не связан с проверками; `fRange_match=True` заглушка; средние FIR taps и обычный `np.hanning` вместо настоящих приватных I/Q coefficients/IDR FFT. Не использовать его для оценки original parity.
2. `MVK_STAGE111Z31AD_CHECK_B_READY.txt`: недействительный `fade_ok` без `je`, отсутствующий `eax_save`, `ebx_save`; `mov eax/ecx` меняет CPU-регистры, недопустим в read-only preflight, непроверенный `dmp`/ `reg` синтаксис. Отказ.
3. `MVK_STAGE111Z31AD_ARM_B_ONLY.txt`: непроверенный `bpwc` и `=` в выражении фильтра; уже существует проверенный ранее `bp`+`bpcond` шаблон v1.5. Отказ.
4. `MVK_STAGE111Z31AD_RESUME_B.txt`: `go` без строгого stage/context guard, не сохраняет full preFFT Power/Y arrays, не даёт подтверждения output или check result. Отказ.
5. `calculate_window.py` и текстовый сценарий: допущение, что можно «подождать 0.5с» на статическом BIN, **необоснованно**; перезапуск MVKView с `StorageOldest=0` также не гарантируется; `rawN+FIR_TAPS` ошибочно как универсальное окно. Оба способа не нужны для **исследования текущего original zero-pad**, хотя отдельно могут понадобиться для испытания **полной истории без нулевого префикса**.

## Новый read-only helper и следующий шаг

Подготовлен проверенный локальный пакет `MVK_STAGE111Z31AE_SAFE_PREFLIGHT.zip`: скрипт `check_original_padded_input.py`, шаблон snapshot JSON, инструкция оператора и 9 синтетических PASS тестов. Сам helper **не использует MCP, не управляет процессом и не меняет память**. Он требует фактические `FRxPos`/FValidPos/high и savedata готового `[EBP-2C]` с EIP14AA, сверяет exact size, нулевой префикс и **необязательно** уникальный битовый нормализованный суффикс с физическим ADC1 BIN. В выдаче не раскрывает исходные измерения, но SHA позволяют контролировать provenance.

Последовательность: **(а)** MPC read-only получить `[Storage+20/24/28/2C]`, `[EBX+14]`, `[EBP-2C]`; **(б)** сохранить **только рабочий preDC** 1048780 bytes при правильном pointer span; **(в)** проверить prefix + BIN suffix Python. **Не F9, не ARM/RESUME, не перезапуск.** При подтверждении исходных байт подготовить новый **защищённый B capture в том же процессе** с поддержкой zero-pad и реальными размерами `FFT N131072` (нужна поэтапная проверка на 153D). Это иной вид parity, чем гипотетический прошлый Stage111Z31AC FIR с **полной** историей для N262144: прежние SHA к текущему вызову не применяются.

**Статус:** ZERO-PAD source PROVED; B рабочий буфер всё ещё **UNVERIFIED** до реального savedata; FIR/FFT/LOG Y ORIGINAL runtime **OPEN**; GitHub содержит только результаты/схемы, не оригинальные исходники, BIN, IDP, FIR banks или dumps.
