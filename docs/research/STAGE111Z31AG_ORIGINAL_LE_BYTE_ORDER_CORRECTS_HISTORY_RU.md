# Stage111Z31AG — исходные RAW little-endian байты показывают WindowEnd 557107, ZERO deficit (2026-11-10)

## Корневая причина ложного Z31R_FAIL_HISTORY: неверная расшифровка GigaCode

Два пересланных сообщения GigaCode содержали первоначальные реальные 4 байта для params `[EBX+20]`: **`33 80 08 00`**. Агент написал `0x00080033=524339`, но это **ошибка преобразования little-endian**: `33 80 08 00` == `0x00088033` == **557107**. В более позднем сообщении GigaCode назвал 557107 «новым WindowEnd после накопления» — это НЕ подтверждено. Исходные байты показывали 557107 с самого начала. **НЕ обвинять агента в фальсификации снимков лишь по изменившемуся десятичному числу**; вместо этого проверить фактическую память двумя независимыми чтениями.

Остальные исходные 4-байтовые поля:
- `[EBX+04] = 33 00 04 00` = `0x00040033` = 262195 (rawN code20)
- `[EBX+08] = 14 00 00 00` = 20
- `[EBX+18] = 00 00 00 00` = 0 (LOG)
- `[Storage+0x28] = 00 80 04 00` = `0x00048000` = 294912 (FValidPos)
- `[Storage+0x10] = 00 00 20 00` = `0x00200000` = 2097152 float32 (ранее GigaCode ошибочно записал 0x00002000=8192)
- `[Storage+0x14] = FF FF 1F 00` = `0x001FFFFF` = 2097151 mask.

**Расчёт для исходного процесса:** `WindowEnd - RawN = 557107 - 262195 = 294912 = FValidPos`. History deficit = **0 Float32**. Никаких автоматических +32768 samples во время Paused НЕ требуется. Прежние Z31AD/AE/AF утверждения о фактической нехватке 32768 для этой остановки были основаны на неправильно интерпретированном LE числе. Считать их **отозванными** для данного исходного состояния.

## Что остаётся верным из старых исследований

Доказательство source `_Unit115.pas`, что `007D2228` в общем случае допускает ZERO-PAD при недостаточной истории, **остаётся корректным**. Однако при указанных текущих исходных bytes source history deficit=0, следовательно для этого вызова **не ожидается нулевой префикс длиной 32768**. Отладчик стоит `EIP=007D14AA` и helper `007D2228` уже создал рабочий Float32 вход в `[EBP-2C]` (work ptr нуждается в прямом read). Дамп должен иметь **262195 Float32, 1048780 bytes**, нужно проверить наличие данных и соответствие реальному ring/BIN. Не выдавать логическое совпадение индексов с BIN за доказанное байтовое совпадение.

`FIR_TAPS[5]=51, DECIM[5]=2`. Из `rawN=262195` source ожидает **postFIR `FFT_N=(262195-51)//2=131072`**, Fs after FIR предположительно 32768, Y half bins **65536**, source stages проверить на EIP153D до full capture. Сообщённое GigaCode `fft_half_bins=131097` — **артефакт старого `Preflight-GetSpectrum.py`**, который при снятии pow2 restriction вычисляет `rawN//2`; это не фактическое число bins после FIR. Дополнительное утверждение `(262195-51)/2+1 = 131097` арифметически неверно (131073).

## Статус инструментария и правила

Последний GigaCode `STRUCTURAL_PREFLIGHT_PASS` получен после правки исходного `Preflight-GetSpectrum.py`, который изначально валидировал rawN как FFT N; **это только структурный офлайн PASS, не доказательство полной FIR/FFT parity**. Изменённый preflight нужно сохранить отдельно и проверить; не перезаписывать исходный инструмент, не запускать имеющийся B шаблон, ожидающий `__N_HEX__=262144`. Исправленный B должен разделять rawN 262195 и downstream FFTN 131072, Y65536; сохранить full raw/DC/FIR/Power/Y/Summary с guard, опираться на исходную логику prefilled work buffer. Готовность RUN ещё не подтверждена.
