# Stage 99 / Native R3 — точное восстановление TCP и проверка расчётных данных

Дата: 2026-10-29. **Источник:** два реальных ранее предоставленных PCAPNG; `_Unit125.pas` из `Projects.7z`; карты регистров производителя и ранее проверенные исследования GitHub. Вся работа — офлайн. Используется собственный `protocol.py`, НЕ `mvk_tcp_reader_v2`.

## 1. Два установленных дефекта Native R2

**A. Сообщение 32800 байт.** В захвате «83 спектр» после идентификационного кадра `type=1, length=264` идёт сообщение `type=0xFF800C0D`, `length=32800`. В нём один адресованный блок `address=0, words=0x4000` (16384 регистра = 32768 байт; полный размер кадра 32 + 32768 = 32800). Оно подтверждается декодированием дескриптора и вместимостью регистрового образа. R1/R2 ошибочно разрешал только длины 44/76/160/4700 и порождал 25 последовательных ошибок заголовка. Исправление: проверять грамматику адресованных блоков для переменной длины, а не жёсткий перечень длин.

**B. Переупорядочение TCP.** В `1111` R2 обнаруживал 16 «пропусков» и 55 ошибок заголовка. После сортировки данных по 32-битному TCP sequence с учётом перехода через 2^32, проверки повторов и перекрытий число **непокрытых диапазонов равно нулю**. Все 16 предполагаемых пропусков заполняются позже захваченными сегментами. Порядок прихода пакетов нельзя принимать за порядок байтов TCP.

## 3. Неоднозначные повторные передачи: не игнорировать

У пяти перекрывающихся TCP-сегментов по одному байту отличается от ранее принятого байта того же TCP sequence. Все пять разногласий отнесены к **160-байтным параметрическим кадрам** `0xFF800C0D`, блок с базой `0x1000`, регистр со смещением `0x0034` (адрес `0x1034`). Ни один из конфликтов не попал в AUX4700. Точный смысл регистра `0x1034` и причина изменения байта при повторе пока не доказаны. Не объявлять это ошибкой DSP, не считать одинаково достоверными обе версии.

Политика по умолчанию: **`reject`** — завершить анализ при конфликте. Только для архивного исследования разрешён явно запрошенный `--overlap-policy preserve_assembled`, при котором сохраняются уже собранные байты, а все конфликты и затронутые кадры заносятся в отчёт. Нельзя использовать этот режим для незаметного исправления производственного потока или записи как непрерывного сигнала.

## 4. Текущие ограничения и безопасность

- R3 офлайн: двухпроходная сортировка сегментов захвата и повторная сборка **не являются кодом Live TCP-клиента**; алгоритм для живого сокета и обязательное первое приложение/рукопожатие ещё требуют анализа оригинального IDR.
- PCAPNG из других сессий, нежели BIN/VALUES прибора №43; совместную временную регрессию с ними не выполнять.
- Нулевая длина непокрытых диапазонов относится к *имеющимся TCP payload* внутри каждого захвата; не доказывает, что захват начинается с начала сеанса и содержит полное окончание. «83 спектр» заканчивается на середине прикладного кадра (988 байт).
- При реальном обрыве R3 отмечает пропущенный диапазон и сбрасывает накопленное состояние. Поиск нового прикладного заголовка требует корректного размера и успешного разбора полного сообщения. **Потерянные данные не синтезируются.**
- У всех проанализированных AUX4700 индикаторы `fs16/fs64/fs512 not ready` не выставлены; **это не относится** к несинхронной записи BIN/VALUES №43.
- Нет отправки сетевых команд, нет подключения к приборам, нет изменения стабильной v0.3.40.
