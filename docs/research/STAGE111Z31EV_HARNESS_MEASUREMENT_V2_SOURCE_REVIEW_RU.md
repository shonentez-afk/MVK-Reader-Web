# Stage111Z31EV — проверка исправленного отчета Harness по оригинальному измерению MVKView

**Дата:** 17.11.2026. **Рассмотрено:** приватные `MVK_MEASUREMENT_FULL_ANALYSIS(1).md` и `MVK_MEASUREMENT_EVIDENCE(1).json` (Harness V2). **Метод:** автономная read-only проверка одновременно `mvkview.idp` (заголовок, сегменты), `Projects.7z` (ранее извлеченные `_Unit125.pas`, `_Unit128.pas`, `mvkform.dfm` с SHA256, совпадающими с SQLite), `mvk_idr(1).sqlite` (функции, call-sites, DFM events). Также выборочно проверен текущий Core+Qt в ветке `research/stage111-mvkview-desktop-20261029`. Оригинальный EXE и прибор не запускались, TCP-команды не отправлялись. **SHA256 локального EXE в Ghidra не сравнивался с оригинальным IDP**, поэтому полная byte identity между двумя экземплярами EXE не доказана.

## Вывод

Вторая версия Harness исправила важнейшую ошибку `Function not found`: оригинальный исходный код по этим адресам существует. Она правильно подтверждает наличие Mode2, TCP/10230 с таймаутами, `GetSpectrum` из фонового потока, обработчиков записи и 10 каналов. **Но объявлять сквозную цепочку измерения полностью восстановленной нельзя:** в отчете остаются фактические ошибки по адресам, назначению функций, ветвлениям, выходным полям и retry; формат сети и полноценный Core+Qt паритет не изучены.

## Проверка источников

- `mvkview.idp`: формат `IDR proj v.3`, ImageBase `00400000`, EntryPoint `008C1DC0`; собственный SHA256 совпал с метаданными SQL-индекса. **Внутренние типы/символы IDP bridge пока полностью не разобраны:** семантическое доказательство имен/полей ниже дано из PAS/DFM + SQLite, а не из гипотетического полного парсера IDP.
- `Projects.7z`: извлеченные копии `_Unit125.pas`, `_Unit128.pas`, `mvkform.dfm` по SHA256 совпали с `source_files` локальной SQLite. Чтение и проверки не изменяют оригинальные файлы.
- `mvk_idr(1).sqlite`: 25 404 функции, 92 767 статических записей вызовов и 95 событий DFM. Подтверждены точные владельцы call-sites и события кнопок.
- Воспроизводимый проверяющий код: `tools/research/verify_mvk_measurement_evidence_v2.py`. На локальных материалах **63/63 проверки PASS**. Это проверки **изначального source-контракта**, а не верности всего текста Harness или исполнения прибора.

## Достоверная схема оригинального Mode2 (статический уровень)

1. `bTaskConnectClick` (`00848E78`) вызывает диспетчер `00846AD4` с `EDX=2`. **Если уже выбран режим 2**, тот же клик сбрасывает режим через `00847040`, а не открывает архив.
2. Перед сетевым соединением Mode2 выделяет **8 ADC + 2 TACH** storage (`00846C67..00846CF1`), показывает четыре дополнительные вкладки и нижнюю панель (`00846D24..00846D84`), создает поток (`00846DCC..00846DD9`), выбирает первый пункт меню частоты (`00846DF7`). Видимость вкладок сама по себе **не доказывает TCP connection**.
3. `TMVKThread.Execute` (`00807A98..00808B68`) создает Indy TCP client, задает **10230**, **1000/5000 ms**, подключается (`00807CA7`), имеет **путь исходящих команд** (`00807E9F..00807F52`) и входящих заголовков (`00807F78`,`00807F84`) с `8 <= frame_length <= 131072`, `length % 4 == 0`. 
4. Разбор каналов и данные: `0080816B..0080828C` читает поля и порции данных; канал проверяется по диапазону `0..9`, блок может передаваться в `TMvkChannelStorage.ProcessBufferChunk`. Другие типы кадров и ответы команд имеют собственные ветки. Точный формат каждого типа/где плавающие значения vs целые — **ещё не закрыт**.
5. `TBackgroundProcessThread.AddTask` (`0084FA58`) принимает код и канал; `Execute` (`0084FA6C`) отдельно обрабатывает **GetSignal** (`0084FAA7`) и **GetSpectrum** (`0084FB03`). После успешного расчета и при `!FTerminated` вызывает `Synchronize` с UI callback (`0084FAD4` / `0084FB2D`).
6. `tmInterfaceUpdateTimer` (`0084F7C8`) вызывает диспетчер видимых страниц `00847248`; это **не** офлайн-перемотка из `0084F7D0`. При сбое/остановке оригинал меняет статус, освобождает TCP client, может повторить connect в Mode2; сравнение с динамическим устройством всё еще открыто.

## Что в Core+Qt уже есть (проверка текущего GitHub)

- `original_runtime_tabs.py` и `test_stage111z31cr_connected_core.py`: в Mode2 модель **5 корневых вкладок** (PageStart, PageStatus, PageAdc, PageSpectrum, PageFile), без предположения о TCP connectivity.
- `original_pagestatus_source.py`: **15** вложенных режимов, включая **две тахометрические** страницы. Поэтому наблюдение «в ADC-графике видно 8 вкладок» не доказывает, что тахометры вообще отсутствуют в совместимом UI.
- `original_mode2_rate_menu_source.py`: пять source-derived `TMenuItem.Tag` в порядке UI **65536, 32768, 8192, 2048, 512**. `original_measure_controls.py` сообщает их как исходно подтвержденные. **В то же время** более старый `original_measurement_pipeline.py` всё ещё возвращает `sample_rate_menu_values_verified=False`; эти metadata необходимо согласовать, не включив аппаратное SetRate.
- Реальный транспорт Native R6.1 остается **read-only**. В отличие от оригинального TMVKThread, он не исполняет SetRate/WriteData/WriteValues on-wire. Это сознательная граница безопасности, не доказательство полного паритета.

## Непринятые части

- Не восстановлены byte-exact **передаваемые слова** для всех категорий команд/ответов и для всех packet type; внутренние 12 байт очереди не являются длиной TCP-кадра.
- Не установлено численное равенство всех режимов FFT/RMS, единиц калибровки и взаимодействия реального прибора; копирование вывода Ghidra этого не доказывает.
- Не выполнен на одной исходной сессии полный UI+Core+transport end-to-end; изменять соответствующее устройство без разрешения оператора нельзя.
- Не сверена полная binary identity `mvkview.exe` на машине пользователя с имеющимися IDP/PAS. Для этого нужен EXE SHA и точечные hex windows.

**Вердикт:** `STATIC_PARTIAL_SOURCE_CONFIRMED`, а не `FULL_ORIGINAL_RESTORED`.
