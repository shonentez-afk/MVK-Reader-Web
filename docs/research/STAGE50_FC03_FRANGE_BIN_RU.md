# Stage 50 — FC03, FRange и запись BIN (2026-10-28)

**Источники, найденные в репозитории:** `docs/PROTOCOL_CALIBRATION_RU.md`, `protocol/mvk_calibration.py`. Это уже известная калибровка, не новое открытие Stage 50.

## Калибровка FC03 (read-only, TCP/502)
Для канала `N=0..7`: база `A=0x0100+N*0x0100`. Чувствительность датчика: `A+0x02`, коэффициент пересчёта `K_Modbus`: `A+0x0E`. Формат `float32 CDAB` с перестановкой двух 16-битных слов. Отдельный системный блок `0x0020`, 16 регистров: восемь коэффициентов калибровки тракта. Подтверждённое ранее соотношение для синхронных пар АЦП4: `a_m_s2 = tcp10230_raw_float32 * K_Modbus`, с точностью float32. Для других каналов независимая проверка не завершена.

## Трассировка записи BIN в IDR
- `_Unit125.pas:0x00808229` — чтение TCP в `TmpStream`.
- `0x00808203` — вызов `0x008020A8` для копирования в рабочий буфер.
- `0x0080828C` — `ProcessBufferChunk(ApplyRange=true)`, на ветви float32 умножение рабочего массива на `FRange` (`_Unit115.pas:0x007D23D5`).
- `0x008082D6` — источник записи в `ChannelFile`: **`TmpStream.FMemory`**, вызов записи через VMT `+0x10` в `0x008082DE`.

**Найдено противоречие, не скрывать:** статическая запись берёт `TmpStream`, а ранее сверенные пары TCP/BIN свидетельствуют о физически масштабированном BIN. Нужно проверить процедуру `0x008020A8` и алиасинг буферов, затем воспроизвести парное побайтовое сравнение одной сессии. Нельзя из текущего дизассемблированного фрагмента заключать, что BIN уже точно raw либо точно scaled.

## Три разные сущности
- `K_Modbus` — коэффициент FC03, источник доказан.
- `FRange` — внутренний множитель `TMvkChannelStorage`.
- `InternalChannelGain` — поле TSXML. Близость значений ещё не является доказательством равенства и единого источника.

**Проверка:** 6/6 структурных адресных опор по IDR локально; численную сверку синхронных TCP/BIN повторно не выполняли. Следующий этап: разбор `0x008020A8`, поиск всех записей `FRange`, проверка одной синхронной пары. Версия v0.3.40 не менялась.

Локальный полный пакет: `MVKVIEW_STAGE50_FC03_FRANGE_BIN_20261028.zip`, файлы `REPORT_RU.md`, `verify_stage50.py`.


## ADDENDUM Stage111Z.23 (02.11.2026): противоречие TmpStream/Storage разрешено

**Актуализирует выводы Stage50, не стирая историю:** статический оригинальный IDR `_Unit125:008081F0..008082DE` показал, что `Storage.AllocBufferChunk` отдаёт pointer прямо в `TmpStream.FMemory` через `sub_008020A8`; `TRecordMemoryStream.SetSize` `008021EC..00802203` не выделяет/не копирует память. `ReadStream` пишет в тот же участок, после него `ProcessBufferChunk(ApplyRange=true)` масштабирует Float32 in place, а `ChannelFile.Write(TmpStream.FMemory)` читает именно **уже масштабированные данные**. Это структурно устраняет прежний блокер «почему Write берёт TmpStream». Оригинальный static source и все условия записи см. [Stage111Z.23](STAGE111Z23_ORIGINAL_LIVE_BIN_POINTER_ALIAS_FRANGE_RU.md).

Добавлено source-evidence: `_Unit125:00806964` берёт TSXML InternalChannelGain через `GetFloatByAddr(0x0E)` канала; `_Unit128:0084655E` при открытии Sidecar кладёт gain в `Storage.FRange`, положительный gain выключает повторный ApplyRange. **Не утверждать**, что одно значение runtime FRange уже доказано для каждого живого канала или что оригинальный и реконструированный BIN одного сеанса совпали побайтово; для этого нужен same-run original capture. Текущий direct BIN не умножает повторно — корректная осторожная семантика.
