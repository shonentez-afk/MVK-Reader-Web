# Stage111Z.23 — оригинальный LIVE BIN writer: разрешён алиасинг TmpStream/Storage и порядок FRange

**Дата:** 02.11.2026. **Метод:** локальный независимый статический аудит приватных оригинальных IDR `_Unit115.pas` и `_Unit125.pas`, БЕЗ сетевого подключения и без запуска оригинальной программы. **Исходный код/дизассемблер не загружены в GitHub**, здесь только адресные опоры и вывод.

## 1. Почему это важно

В Stage50 отмечено кажущееся противоречие: `ProcessBufferChunk(ApplyRange=true)` умножает входные Float32 на `FRange`, но `ChannelFile.Write` получает указатель `TmpStream.FMemory`, а не отдельно выделенный подшипниковый/ADC storage буфер. Отсюда нельзя было доказать: BIN оригинальной MVKView сохраняет сырые или уже масштабированные float32.

Установлено, что **TmpStream НЕ владеет второй копией данных**: его `FMemory` — непосредственный алиас буфера хранения `TMvkChannelStorage`. Поэтому место вызова `ProcessBufferChunk` до `ChannelFile.Write` решает вопрос о порядке масштабирования.

## 2. Адресная цепочка из реального оригинального IDR

| Адрес | Подтверждённая операция |
|---|---|
| `_Unit115:007D1B08..007D1B43` | `TMvkChannelStorage.AllocBufferChunk` возвращает `PAdcFloatData + (FRxPos & mask)*4` в Float-ветке |
| `_Unit125:008081F0..008081F6` | Для выбранного Storage вызывает `AllocBufferChunk(var Size)` и получает указатель в EAX |
| `_Unit125:008081FB..00808203` | Указатель в EDX передаётся в `sub_008020A8(TmpStream, pointer)` |
| `_Unit125:008020A8..008020B0` | `sub_008020A8` делает `[TRecordMemoryStream+4] = pointer`, `FPosition=0`; **не выделяет память** |
| `_Unit125:0080820E..00808213` | `TRecordMemoryStream.SetSize` |
| `_Unit125:008021EC..00802203` | `SetSize` изменяет только `FSize` и при необходимости позицию — **не меняет `FMemory`** |
| `_Unit125:00808229` | `TIdIOHandler.ReadStream` пишет входные данные в stream |
| `_Unit125:00802204..00802263` | `TRecordMemoryStream.Write` через `Move` пишет непосредственно по `FMemory+FPosition`; отдельного буфера/копии нет |
| `_Unit125:00808284..0080828C` | Вызывает `TMvkChannelStorage.ProcessBufferChunk(Size, ApplyRange=true)` |
| `_Unit115:007D23B7..007D23E5` | Если тип Float32 (`FAdcDataType==0`), `PAdcFloatData[k] <- Single(PAdcFloatData[k]*FRange)` **in place** |
| `_Unit125:008082AD..008082C1` | При `WriteDataStage=1` и наличии ChannelFile разрешает запись BIN |
| `_Unit125:008082D0..008082DE` | `ChannelFile.Write(TmpStream.FMemory, Size)` читает **тот же указатель** уже ПОСЛЕ `ProcessBufferChunk` |

При отсутствующей Storage-структуре `_Unit125:008082F6` пишет во временный DummyBuf без соответствующей нормальной ветви ChannelFile. Есть проверки `MvkSampleRate` и `FreezeUpdate`; нельзя переносить вывод на некорректные или отключённые записи.

**Вывод с высоким уровнем уверенности для именно этой штатной live-последовательности:** сохранённые оригинальной программой Float32 BIN-байты содержат результат выполненного в памяти `Single(raw*FRange)`, если применяется Float-ветка и активна запись ChannelFile. В Byte/Count ветке такого множителя нет.

## 3. Согласование с ORIGINAL TSXML reader

- В генераторе TSXML `_Unit125:00806964..00806985` InternalChannelGain берётся из канальной таблицы по `GetFloatByAddr(0x0E)`, то же смещение исходной карты Modbus, что и K_Modbus. Но отдельное доказательство фактического значения `FRange` **конкретного живого Storage** в каждом измерительном режиме по-прежнему требует runtime-снимка; автоматически приравнивать переменные для всех каналов не следует.
- При чтении оригинального BIN original `_Unit128:0084651F..00846522` с положительным internal gain передаёт `ViewedFileIsNormalized=false`, и `ProcessBufferChunk` **не умножает сохранённые байты повторно**. Сгенерированный writer, если gain=0, подставляет 1.0; при fallback `DefaultConfig.txt` возможен иной механизм, который здесь не аттестован.
- Наш текущий `DirectBinSession` корректно оставляет исходные Float32 без повторного умножения. В интерфейсе FRange объявлен **метаданным кандидатом**, не новым автоматическим коэффициентом масштабирования. Это теперь согласуется с исходной цепочкой буферов, но не является универсальным proof of original BIN для произвольно переименованных/преобразованных записей.

## 4. Что ещё НЕ установлено

1. Побайтовая идентичность оригинального BIN и сетевого ADC10230 потока *одного и того же физического сеанса* не проверена в этом этапе.
2. Источник и runtime-значение `TMvkChannelStorage.FRange` при настройке прибора требуют отдельной трассы для всех ADC/типов и изменений конфигурации.
3. При пересечении кольцевого буфера `AllocBufferChunk` может ограничивать `Size` до края; исходный цикл `008082E1..008081EA` отрабатывает несколько частей. Статическая схема допускает этот путь, а точное численное накопление многоканального сеанса — отдельная проверка.
4. Содержимое `Byte` счётных каналов, заголовки иных исходных вариантов, фрагменты повреждённых архивов — отдельные форматы. Их нельзя интерпретировать как Float32 в нашей программе.

## 5. Практический результат

**Старый Stage50 «aliasing unresolved» снят на уровне original static code:** TmpStream.FMemory и Storage.AllocBufferChunk действительно указывают на одни данные; `SetSize` их не копирует. Само содержимое сохранённых Float32 может уже быть `FRange`-масштабированным. Это предотвращает классическую двойную калибровку при восстановлении оригинального чтения.

Следом — source map присваиваний live `Storage.FRange`, затем оригинальный capture от TCP → live BIN → повторное чтение BIN → GetSignal/GetSpectrum на одинаковом ADC/времени. Старый source FFT и его реальные x32dbg goldens не менять. Стабильный main и Web не трогать, никакого подключения к реальному прибору.
