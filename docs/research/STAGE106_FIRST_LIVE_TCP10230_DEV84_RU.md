# Stage 106 — ПЕРВОЕ подтверждение Native R5/R5.1 на реальном МВК01 №84

Дата: 2026-10-29. **Результат: LIVE READ-ONLY PASS** на одном реальном приборе за две независимые 30-с записи. Стабильная MVK Reader Web **v0.3.40 не затрагивалась**. Источники: два отчёта тестера из `TEST_2026-10-29_11-33-56.278.7z` и `TEST_2026-10-29_11-41-01.306.7z`; два соответствующих пользовательских Wireshark `84 тест.pcapng`, `84 тест 2.pcapng`. **Сырые PCAP/RAW и фабричные адреса в GitHub не загружались**.

**ВАЖНАЯ версия:** №1 (11:33:56) выполнялся **Native R5 1.0**, №2 (11:41:01) — **Native R5.1 1.1 (Ethernet-bound)**. Неверно обозначать оба R5.1.

В R5.1 выбран **Ethernet NIC index 20**, исходный IPv4 привязан; в обоих PCAP описание Npcap-интерфейса **Ethernet**. TCP-тройное рукопожатие штатное; **от клиента к прибору 0 байт прикладных payload** на двух сессиях. Первый приборный payload после SYN через ~12.15 мс / ~0.98 мс. **TCP Connect достаточен для активации выдачи потока**, команды запуска не нужны.

## Побайтная независимая проверка

**TCP reassembly из PCAPNG**, отдельно от R5/R5.1:
- №1: со стороны прибора 69 678 520 unique байт, TCP gaps=0, overlaps=0. **Первые 69 675 600 B побайтно равны `incoming.raw`**, включая SHA256 префикса `e001bbb94f375403bcb38031dd5b18376d04d48f9f0cdff39bd792e009aa1d66`. В PCAP после конца программы осталось 2920 B: два полных ADC кадра и 816 B следующего.
- №2: со стороны прибора 69 686 496 unique байт; TCP gaps=0. **Три перекрывающихся retransmit (4356 B)** отличаются от более ранних копий **ровно пятью байтами**: внутри трёх 160-B PARAM-контейнеров по регистрам **0x1024** (1 B) и **0x1034** (4 B). В `incoming.raw` R5.1 имеются поздние версии этих пяти байтов. В ADC/TACH/AUX4700 различий не найдено. После момента закрытия программы в PCAP дополнительно 6688 B. При исследовании PCAP ни одна неоднозначная версия retransmit **не должна молча подменяться**.
- Значения пяти изменённых служебных байтов не означают реальный дефект ADC; причины конфликтующей retransmission (переиспользование буфера — лишь гипотеза) пока не установлены. Эта проблема уже встречалась в старых PCAP; сохранить forensic conflict policy для offline import.

**AUX4700 независимым парсером:** просмотрены последовательные регистровые сообщения из `incoming.raw`; для каждого из 60 обновлений × 8 каналов сравнивались 43 третьоктавных RMS, 24 band RMS, 24 peak-equivalent, 24 span-equivalent и 1 статус. **55 680 + 55 680 = 111 360 полей сравнились строго по float32/uint32; 0 несовпадений**, 0 NaN/Inf. Это подтверждает декодирование регистров, **не** точный DSP-расчёт из исходных временных данных.

## Непрерывность исходных измерений и калибровка

- Первые 264 B identity одинаковы в обеих сессиях (SHA256 `b58d23968208339f64754c4327df420703a63309b46aa860e8a0b83b75e46a2c`).
- Во всех восьми каналах **разность начальных ADC-индексов = 27 845 120**. При Fs=65536 Hz это **424.8828125 с** между ними; часы ПК показывают 424.891683 с (около 9 мс разницы). **Счётчик ADC не перезапускается при новом TCP Connect** — поток выдаётся из постоянно измеряющего устройства.
- Все 8 индивидуальных K (gain) из начала текущего TCP-сеанса **совпали между тестами**. ADC1–8: 510.56503, 512.09833, 509.71161, 510.21976, 513.79242, 509.60764, 509.32312, 508.74240. Sensor sensitivity везде ~0.010194 В/(м/с²).
- Для проводного `ADC1052` — `raw float32 × проверенный gain текущей сессии`; готовый MVKView BIN уже откалиброван и повторно умножать нельзя.
- ADC1–6: во всех AUX обновлениях статус `0x00000000`; ADC7 и ADC8: `0x00000400` во всех 120 суммарных обновлениях каждого канала. Вероятно сигнал **обрыва линии/превышения максимального напряжения датчика** (согласно ранее разобранным status flags); **не считать** ADC7/8 исправными только на основании присутствия фреймов.
- AC RMS полного временного диапазона (калиброванный, это **не** 10..3000 Hz): ADC1 6.9094→6.9404 (+0.45%); ADC2 13.4904→14.8719 (+10.24%); ADC3 8.5445→8.2101 (−3.91%); ADC4 13.2864→13.3666 (+0.60%); ADC5 9.3647→9.1705 (−2.07%); ADC6 15.2534→16.3548 (+7.22%); ADC7/8 в статусе 0x400 не интерпретировать как здоровые измерения.

## Что теперь можно и нельзя утверждать

**Подтверждено реальным hardware:** TCP/10230 Ethernet read-only Live, автоматическое начало потока при подключении, отсутствие исходящего приложения, приём 8 ADC + 2 TACH, стабильная непрерывность индекса, 60 × 8 каналов AUX, точный регистровый декодер, фактическая привязка NIC в R5.1.

**Ещё не подтверждено:** точная оригинальная DSP-математика, полное двоичное совпадение будущих BIN/TSXML с MVKView, CSV VALUES/TABLE, аварийный reconnect и многочасовые сессии. Исследуемая прошивка Blackfin — отдельный трек Stage104, не препятствует сетевой разработке.

## Stage107 / ближайший шаг

**Перейти к 8-канальному fail-closed BIN/TSXML recorder + VALUES/TABLE** на основе собственного Native ядра (не `mvk_tcp_reader_v2`), с индивидуальными K из начала того же сеанса, контролем index +=256, atomic write/rollback и отдельной сверкой с MVKView. Сначала разработка **офлайн на этих реальных 30-с сохранённых RAW**, без подключения к производственному прибору; лишь затем согласованный полевой тест. Stable `v0.3.40` не трогать.
