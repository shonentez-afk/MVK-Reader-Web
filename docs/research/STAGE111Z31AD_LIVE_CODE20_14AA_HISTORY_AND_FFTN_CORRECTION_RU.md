## Две исправленные ошибки отчёта GigaCode

**Точное текущее начало окна:** `end - raw_n=524339-262195=262144`. Проверка `start >= oldest` не проходит: `262144 < 294912`, **недостача 32768 Float32 (0.5 sec at 65536Hz, 131072 bytes)**, а не 262195. Ёмкость ring 2097152 Float32, но это НЕ отменяет logical oldest. Нельзя заявлять, что байты перезаписаны: memory availability без привязки к source still unknown. Существующий v1.5 `RESUME_B` сейчас **не запускать**: остановится `Z31R_FAIL_HISTORY`, в случае других полей возможно раньше.

**Реальный исходный rawN для code20:** `262195 = 2*131072+51`. Source-derived single stage5 IQ: `FIR_TAPS[5]=51`, `FIR_DECIM[5]=2`, `pre_stage=second_stage=None`, `n=(rawN-51)//2=131072` выходных отсчётов. Следовательно при `007D153D` **вероятный** FFT N131072, output Fs32768, df=0.25 Hz, Power/Y **65536 Float32/262144 bytes**, НЕ predicted 262144 FFT/131072 Y from previous Stage31AC offline candidate. Этот output FFT N нужно **физически подтвердить** `[EBX+04]` на preFFT, без F9/выполнения. Прежний model candidate N262144/df0.125 из Stage31AC — корректная отдельная **модель для гипотетического более длинного окна**, но **НЕ эталон живого B из текущего EIP14AA**, и его SHA нельзя требовать от данного B.

**Непригодность старого шаблона B v1.5 без адаптации:** в postFIR preFFT на `007D153D` шаблон сравнивает `[EBX+04] == __N_HEX__`, затем postFFT `[EBX+28] == __HALF_N_HEX__`, ожидая из старой `-N 262144` power/Y по 524288 bytes. Для нынешнего B нужно при доказанном N131072 предусмотреть **собственные guards** rawN262195, expected OutputN131072 и half65536 и (если preflight подтверждает) байтовые размеры; не ослаблять guard для подгонки. Старый plain A N262144 нельзя без изменения схемы валидатора парить с B N131072; основывать приёмку на full physical original BIN bytes и отдельном B-only check.

## Что дальше

Сейчас **только чтение** EIP14AA, проверить логические поля earliest available, last write и фактическую связь с ADC1 BIN; никакого `F9`, `ARM_B`, `RESUME_B`, повторного LOG, ручной записи памяти. Для условий `start>=294912` при rawN262195 потребовался бы **end>=557107** (на 32768 позже), если GUI/оригинал позволяют выбрать более поздний участок того же BIN и предварительная физическая идентификация bytes подтверждает его; это лишь необходимая арифметика, не утверждение о доступном GUI действии и не гарантирует raw/FFT equality.
