## 2. Что именно в ПОСЛЕДНЕМ плане было избыточно

В Stage29C1 и master plan встречалась фраза `Stage29C2 original GetSpectrum storage FRange division-before-FIR input domain OPEN`, которую можно прочитать как необходимость **впервые исследовать** исходное деление на FRange. ЭТО НЕВЕРНО: источник и нормальный float-ring branch **давно доказаны и реализованы** Stage111J. Новая задача Stage29C2 должна называться **`Envelope GetSpectrum integration + original runtime input-window parity`**: использовать проверенный `prepare_original_fft_input(..., input_domain='original_float_storage')` перед FIR, но только по ЯВНО выбранному и доказанному original source-domain, без двойного применения gain, и получить real x32dbg pre-FIR / post-FIR / pre-FFT равного окна.

Текущий `OfflineSession.spectrum_envelope()` **НЕ принимает `input_domain`**; напрямую передаёт калиброванные BIN в `envelope_spectrum_idr_candidate`, а `process_original_envelope_candidate()` удаляет DC и фильтрует без дополнительного параметра original_storage. То есть это **не новая неизвестная операция**, а незавершённая интеграция уже source-verified операции в ветвь огибающей. Не менять байты сохранённого BIN и не делить его на FRange без доказанного режима original float ring.

**Нельзя заново требовать от оператора** original `after_power(1)`, `summary_power.bin`, 4 mode VScale words, Tag0 triplet, скриншот или Copy 6,89/3800/0,7786: эти результаты уже есть и сохранены. Но они относятся к исходному FFT OUTPUT/Tag0 и графическому масштабу, а не к возвращённому буферу функции `GetSignal` или исходному pre-FIR input.

## 3. Что реально отсутствует — формальные DATA GATES

1. **Stage29B original GetSignal return:** в текущих пользовательских `Projects.7z` (source) и `mvkview.idp` (IDA database), репозитории/доступных локальных файлах не обнаружен независимый **после GetSignal `OutputLength×Float32` reverse return** от живого исходного Win32 процесса. Старый `before_fft(1).bin` содержит уже **ПОДГОТОВЛЕННЫЙ К FFT**, а не GetSignal return; он не заменяет этот эталон. В текущей рабочей среде оригинальные `before_fft(1)` / `after_power(1)` физически также НЕ смонтированы — есть только их проверенные прежние метрики/SHA в отчётах. Не требовать повторно capture, если пользователь может указать/подключить существующий прежний дамп, но не утверждать, что он точно подменяет GetSignal.
2. **Stage29C2 envelope:** original pre-FFT `before_fft(1)` **мог** содержать огибающую, так как снимался после подготовительного кода. Однако исторический manifest не содержит `[EBX+08] EnvelopeCode`, ADC, точные Float32 source BIN windows, FAdcDataType/ViewedFileIsNormalized и подтверждение того же вызова. Без этих данных нельзя объявить оригинальную FIR нумерическую паритетность; не отождествлять 131072/131072 FFT success с фильтрацией FIR.
3. **Stages30 S04/S05/S06:** реально нет ПОЛНЫХ исходных after-mode численных массивов GetSpectrum для Tag1/2/3, одинаковых ADC/N/window/FRange; четыре оригинальных слова x87 VScale из StageZ2 этим **НЕ являются**.
4. **S08:** есть оригинальный screenshot и одна Copy запись, но нет paired Qt PNG на идентичной геометрии и всего оригинального `TQGrapher/Canvas` pixel diff; три Copy поля ≠ полнота всех режимов и raw-clipboard bytes.
5. **Stage27B:** byte-identical original BIN+TSXML и Native R6 ZIP **одного подтверждённого сеанса** не было. Stage109 real hardware PASS/84k frames = собственная проверка Go протокола, не Original Delphi same-run.
6. **Stage26C/32:** live N65536/N262144 long ring и длительные реальные аппаратные проверки нового Qt EXE остаются OPEN.
