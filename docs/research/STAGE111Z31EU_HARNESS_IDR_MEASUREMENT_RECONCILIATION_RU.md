# Stage111Z31EU — проверка отчёта DeepSeek Harness о полном измерении MVKView

**Дата:** 17.11.2026. **Основа:** переданные пользователем `MVK_MEASUREMENT_FULL_ANALYSIS.md` и `MVK_MEASUREMENT_EVIDENCE.json`, повторно открытые приватные `/mnt/data/mvkview.idp`, `/mnt/data/Projects.7z`, `/mnt/data/mvk_idr(1).sqlite`. **Среда:** разбор статических файлов, без запуска EXE, UI или прибора. В GitHub помещена только производная карта и тестовый анализатор — не приватные исходники/дампы/полные отчёты пользователя.

## Вывод

Отчёт Harness содержит важные верные участки по GetSpectrum, GetSignal, буферам и очереди, но его ключевой отрицательный вывод «кнопка Измерение и большая часть TMVKThread отсутствуют в оригинале» **опровергнут исходными материалами**. Причина: `get_function_info` в Ghidra возвращает `Function not found` для адреса без определённого **Ghidra Function object**, даже когда по адресу находятся действительные инструкции оригинальной программы. У `TMVKThread.Execute` Ghidra также оборвала функциональную область значительно раньше настоящего конца. Это дефекты/ограничения текущей базы анализа Ghidra, не доказательство отсутствия кода в EXE.

## Реальная машинная карта (сверено по трём источникам)

`mvkview.idp`: IDR project v3; оригинальный image base `00400000`, entry point `008C1DC0`. Заголовок/сегменты и SHA256 IDP прямо проверены; внутренняя база IDP в бридже **не декодирована полностью**. Точные имена/адреса ниже получены из PAS/DFM `Projects.7z` и SQLite-индекса тех же исходников, а не из неразобранных внутренних таблиц IDP.

Автоматический проход по 24 адресам из JSON дал: **17** `found=false` в Ghidra; из них **10** — документированные входы в функции, **7** — существующие инструкции внутри более крупных функций; **0** адресов не подтверждено в PAS по адресу инструкции.

### Серьёзная потеря тела TMVKThread.Execute при декомпиляции

Harness считал `TMVKThread.Execute` законченной на `00807BA5`, показал 270 адресов и три базовых блока. Исходный PAS показывает настоящую процедуру **`00807A98`–`00808B68`** с условными ветками и SEH. Примеры статических контрольных точек:

|---|---|

| `00807C29` | `SetConnectTimeout(1000)` |
| `00807C39` | `SetReadTimeout(5000)` |
| `00807CA7` | `TIdTCPClientCustom.Connect` |
| `00807E9F` | проверка внутренней очереди `TMVKThread.CommandList` |
| `00807EC2` | `TThread.Synchronize` для получения очередной команды |
| `00807F52` | `TIdIOHandler.Write` для командных данных |
| `00807F78`, `00807F84` | два исходных `ReadUInt32` для заголовка кадра |
| `00807F94` | проверка верхней границы длины кадра `0x20000` и кратности четырём |
| `0080828C` | `TMvkChannelStorage.ProcessBufferChunk` |

Следовательно, вывод «Execute содержит только CSV-дампер» **неверен**. Оригинал содержит сетевое чтение и записи, реальный формат которых ещё требуется проверить по всем веткам. Никаких сообщений прибору не передавалось.

### Второй путь спектра и ошибка атрибуции вызовов меню

`0084FB03` — вызов `GetSpectrum` из `TBackgroundProcessThread.Execute` (дополнительно `TThread.Synchronize` для UI-обновления). Значит, найденные Harness переходы через `sub_00848148` **не исчерпывают** тракт.

Вызовы `sub_00848148` по `0084C50A`, `0084C5A0`, `00847294` из отчёта верны, но владельцы первых двух **перепутаны**: `0084C50A` находится в `Tmvkform.mSpecLines1Click` (`0084C4C8`), `0084C5A0` — в `Tmvkform.mSpecType1Click` (`0084C514`). `00847294` принадлежит обновлению активной страницы `00847248`. `mSpecVScale1Click` начинается только с `0084C5AC`; нельзя приписывать ему предыдущую инструкцию.

### Методологические ограничения и поправки

- Внутренний элемент очереди `QueueCommand` действительно имеет **12 байт**, но это **не** доказанная длина передаваемого по TCP пакета. Сначала проверять путь сериализации `0080937C` → `TIdIOHandler.Write`.
- Строки `ConfigModbus*` говорят о **возможности конфигурации Modbus**, но не доказывают, что исходный поток измерений на TCP/10230 является протоколом Modbus/TCP. Он содержит собственный фрейминг. Без просмотра заголовка и всей ветви чтения нельзя писать «Modbus/TCP — подтверждённый транспорт измерения».
- Поле `TMVKThread.MvkSampleRate` действительно имеет смещение `+0x400D0` в исходном классе потока; размер объекта объясняется другими полями/массивами и **не** доказывает, что `this` — указатель формы.
- Отрицательные результаты `get_function_info`, `get_callers`, `list_functions` означают только недостаточность/особенность размеченной базы Ghidra. Для проверки использовать точные инструкции по адресам, `get_hexdump`, `get_disassembly`, `get_xrefs_to` и PAS/DFM/SQLite.
- Не путать six-way dispatch (включает скрытые/конфигурационные страницы) с числом видимых вкладок на экране. Исходный Mode 2 раскрывает 5 основных вкладок до TCP-соединения; конфигурационные страницы управляются отдельно.
- Прямое чтение SQLite в режиме `mode=ro` и извлечение PAS из копии архива в отдельный временный каталог **не изменяют оригинальные входные материалы**. Поэтому отказ Harness анализировать все три файла не был технически необходим.
- Даже наличие всех статических путей не даёт автоматического утверждения о полной функциональной и численной эквивалентности. Точный on-wire протокол, пять SetRate значений, ошибка/retry-паритет и оригинальный UI/RMS/FFT паритет требуют отдельных подтверждений.

## Исправленная приёмка

- **VERIFIED_STATIC**: исходное начало обработчика кнопки, двухуровневая маршрутизация Mode 2, наличие TMVKThread TCP/10230 с тайм-аутами, внутренней очереди и передачи, двух ReadUInt32, typed exceptions, фонового GetSpectrum и GUI synchronization.
- **UNVERIFIED**: полный разбор каждого типа кадра, точные исходящие пакеты по всем командам, честный десятиканальный реальный поток, точные частоты 5 пунктов меню, восстановление всех UI/расчётов и полный machine parity.
- **Следующий этап**: разобрать `TMVKThread.Execute` по действительным адресным диапазонам, синхронизации и источникам, не обрывая её по ошибочной границе Ghidra. Потом выполнить Core+Qt интеграцию и тесты, не отправляя аппаратные команды без отдельного подтверждения.

## Непосредственная инструкция для локального Harness

1. Переоцени утверждение «не существует» по 17 адресам, не изменяя оригинальный EXE.
2. Прочитай реальные инструкции по адресам `00848E78`, `00846AD4`, `00807C18`, `00807C29`, `00807C39`, `00807CA7`, `00807E9F`, `00807F52`, `00807F78`, `00807F84`, `0080828C`, `008088A2`, `008088CE`, `008088FA`, `00808923`, `0084FB03` — даже если `get_function_info` возвращает not found. При отсутствии листинга изучай сырые байты и не делай вывода об отсутствии функции.
3. Прочитай три локальных источника (IDP-header, PAS/DFM, SQLite `mode=ro`) вместе, сопоставь владельцев call-sites и исключения. Для архивных PAS используй отдельную копию/временный каталог. Приватные пути, сырые исходники, приборные IP и дампы не публиковать.
4. Пройди `TMVKThread.Execute` от `00807A98` до `00808B68` блоками по адресу и проверь исключения/`TIdIOHandler`/`TThread.Synchronize`; `0084FA6C` + `0084FB03` — независимо.
5. Исправь локальный отчёт и JSON: `found=false` заменить на `not_defined_as_ghidra_function`, добавить `source_presence` и честный `static_scope`; отметить незакрытые wire и runtime пункты. Никаких записи Ghidra DB, внешних подключений или TCP-отправок.
