## Что было неверно в Native, и что теперь восстановлено

| Контракт | Delphi MVKView 1.0.47 | Native ДО | Native ПОСЛЕ |
|---|---|---|---|
| Измерить | `bTaskConnectClick` выбирает Task2; один `TIdTCPClient` на IP/10230 | Один Go-клиент | Сохранено |
| Запуск потока | Stage0 на каждом новом соединении, Stage1 после первого непустого PARAM | В основном восстановлено | Сохранено |
| FIFO | До **каждого следующего прикладного пакета** источник отправляет максимум одну команду | Отправка только перед очередным **OS TCP Read**; склеенные пакеты нарушали порядок TX/RX | **Отправка между склеенными пакетами** + перед OS Read; FIFO по исходным границам |
| Условие SetRate | `Stage==1` + непустая `CommandList`; никаких дополнительных проверок `Status0==0` в точке `00807E8F` | Второе требование `status0Seen && status0==0`, задерживало оригинальную команду | Условие совпадает с веткой `Stage1`; уже наблюдавшаяся ненулевая системная ошибка ставит Stage3 и блокирует отправку |

## Подтверждение пакетного поведения на локальном TCP

Добавлен `source_task2_packet_interleaved_full_cycle_test.go`:
- Один `ProcessChunk` с непустым PARAM (без Status0) и тремя ADC; **три реальные передачи** по одному `net.Pipe`, FIFO точно `SetRate(65536)`, `SetRate(32768)`, `SetRate(8192)`, каждая 36 байт, без второго сокета. Индексы АЦП/RAW и счётчики сохраняются.
- Новый сокет после реального `Status0=42`, затем непустой частичный PARAM без Status0: нельзя наследовать чужой `Stage3`; `FreezeUpdate` не создаёт липовый статус, а две части `Status0` объединяются из этого сокета.
- Доказанное ненулевое **нижнее или верхнее** 16-битное слово `Status0` сразу блокирует TX; одно лишь неполное значение не выдаётся за целое.
- Две перекрывающиеся записи `Status0` **в одном PARAM** должны оцениваться по последней исходной записи, прежде чем latch Stage3.
- Непустой PARAM + DENIED + ADC в **одном** сетевом чанке: допустимый SetRate перед DENIED, затем Task2 abort, никаких ложных декодированных ADC; исходный `incoming.raw` побайтово соответствует реально поступившему чанку.

Оригинальные сетевые команды должны уходить только через существующий единственный Native Go socket. Пользователь разрешил необходимую оригинальную передачу для восстановления; **физическая отправка в этой среде не проводилась**, так как сеть МВК01/его NIC здесь недоступны. В настольном приложении оператор видит отдельный переключатель исходного `SetRate` и подтверждение соединения. Task3/4/5, Flash, Reboot, изменение IP не требуются для исходного `bTaskConnectClick` Task2.

## Первоначальный SetRate при самом нажатии «Измерить»

Проверка `_Unit128.pas` `008457F1..0084587B`: пять частот создаются из таблицы `gvar_008D2F7C`, каждый пункт вставляется в `popSampleRate.Items.Insert(0)`, поэтому первый пункт меню соответствует последнему (наибольшему) элементу таблицы; `FormCreate 00844308..00844310` выбирает элемент таблицы `+10h` как начальную частоту. Именно **первый элемент сформированного меню** передаётся в `mRate1Click` сразу после `TMVKThread.Create` в `bTaskConnectClick 00846DDF..00846DF7`. `mRate1Click 0084DF03..0084DF18` записывает `SelectedSampleRate` и вызывает реальный `TMVKThread.SetRate` даже до подключения TCP. `TMVKThread.Create` инициализирует `MvkSampleRate=0x309` (777), поэтому выбор 65536 ставит команду в FIFO. Нынешний Go `newSourceLiveTask2TX` ставит `65536` в очередь, что **совпадает с подтверждённой исходной стандартной раскладкой**. Пользователь разрешил такую передачу в разговоре; реального прибора/NIC у среды нет, физическая передача здесь не выполнялась.

**После этого пакета:** оригинальный путь «Измерить» теперь по умолчанию включает `source_rate_tx`, и Native отправляет начальную `SetRate(65536)` через единственный Task2 TCP. Режим отдельного Native-приёмника без оригинального Mode2 **по-прежнему пассивен по умолчанию**, а при запуске настоящего промышленного подключения пользователь обязан отдельно подтвердить выбранный Ethernet и явным **Yes** подтвердить предупреждение об исходящей SetRate; всё можно переключить в пассивный приём. Во время записи флажок нельзя переключить так, чтобы он ложно показывал отсутствие разрешённого TX. Это осознанное UX-отличие от бесконтрольного оригинального старта, но уже не дополнительная пассивная блокировка исследовательского Mode2. Пользователь разрешил восстановление исходящей части протокола.

## Существенные открытые отличия — не выдавать за полный 1:1

1. При **недопустимом кадре** оригинал выбрасывает исключение и может переподключаться; Native сохраняет всю форензику и может переходить в `captureOnly`. Требуется аппаратно подтверждённая исходная политика выброса/повторов без потери RAW.
2. Оригинальный `TMvkChannelStorage.ProcessBufferChunk(Size,ApplyRange)` применяет `FRange` через x87 `fld/fmul/fstp` к Float32 во время приёма. Native использует отдельно проверяемую калибровку и `FRange=1` для уже нормализованных значений; точный численный parity/x87 **не доказан**.
3. Оригинальный Task2 делает повторные подключения в своём цикле; Native требует отдельного разрешения на новый TCP после первого RAW, чтобы не произвести неожиданный аппаратный сеанс. Это сознательное UX/безопасностное отличие.
4. Граница нажатия `WriteData/WriteValues` в Qt журналируется на следующем декодированном кадре, но Win32 микровременной порядок UI/Сoncurrent `Synchronize` не доказан.
5. Реальный МВК01 с сопоставимой PCAP/Win32 сессией, поведение DENIED/таймаутов/ошибок/смены Fs/Stop и BIN/TSXML/CSV требует аппаратной приёмки.

**`original_delphi_compatibility_verified=false` остаётся без изменений.** Программный CI — не аппаратный 1:1.
