# Stage111Z31V — аудит полного GigaCode MCP-отчёта obmen

Дата: 09.11.2026. Источник: [main/obmen](https://github.com/shonentez-afk/MVK-Reader-Web/blob/main/obmen), получен оператором с GigaCode → x64dbg Automate MCP → x32dbg. Это **текстовый отчёт модели**, а не сами байты сырых MCP read_memory и не end-to-end исходный Win32 capture.

## Операторский снимок и границы знания

GigaCode сообщает: EIP=007D14AA, EBX=02A40E58, EBP=0019F270, ECX=7E510010, EAX=00040000, N=[EBX+04]=262144, EnvelopeCode=[EBX+08]=0 (plain A); Storage=[EBP-4]=02B28850, FAdcDataType=[Storage+0C]=0. Подключение MCP и достижение GetSpectrum правдоподобны, но **заявления GigaCode о размере спектра 4096 и очередности стадий ложны**. Actual [EBX+18] (SpectrumMode) в отчёте НЕ прочитан; «SpectrumMode=1» ошибочно взят из [EBX+0C] и не даёт mode-proof. Не делать F9/6 single-shot BP на этой основе.

## Воспроизводимые ошибки little-endian/Float32 в предоставленном отчёте

| Поле / байты | Заявление GigaCode | Перепроверено стандартным struct.unpack('<I' / '<f') |
|---|---|---|
| Storage+18 `00 00 01 00` | 0x00000100, Fs=256 | **0x00010000, Fs=65536** |
| Storage+04 `53 48 FF 43` | FRange≈510.28 | **510.5650329589844** (0x43FF4853) |
| Data+00 `50 B5 AA BD` | Float32≈-0.000001 | **-0.08335363864898682** |
| Data+04 `E0 0B B7 BD` | Float32≈-0.000002 | **-0.08937811851501465** |
| Data+08 `30 77 BD BD` | Float32≈-0.000014 | **-0.09251248836517334** |
| Data+0C `BD B0 03 BF` | Float32≈-2.563 | **-0.5144155621528625** |
| Storage+10 `00 20 00 00` | ring capacity 8192 | Если именно эти байты — 8192, но противоречит маске 0x1FFFFF и старому реальному кадру; проверить заново непосредственно MCP, не угадывать. Для 2 097 152 байты будут `00 00 20 00` |

Несоответствия кодов/чисел указывают на **недостоверную интерпретацию в текстовом отчёте GigaCode**. Нет доказательства, что сам MCP read_memory повреждает память или даёт неверные байты; для такого вывода нужны сырые результаты его инструментов.

## Правильная исходно-проверенная цепочка GetSpectrum

Сверено с сохранённым [capture Stage111Z31R v1.5 A](../../tools/research/stage111z31r_x32dbg_two_mode_capture/RESUME_A_FROM_14AA.template.txt) и B:

- **007D14AA**: входной рабочий Float32 массив до снятия DC / огибающей, `[EBP-2C]` pointer, параметры из EBX;
- **007D14B8**: после DC, **не «после Envelope»**;
- **007D153D**: после FIR/decimation для режима B или plain A, **до FFT**;
- **007D154B**: после FFT, исходный массив **Power до преобразования режима**;
- **007D17E7**: Power **после** преобразования режима и `[EBP-30]` полная кривая **Y**;
- **007D1900**: проверенная точка итоговых трёх Float32 слов `[EBX+30/34/38]` (не смещать на `007D18FF` без исходной проверки).

Старые операторские golden: N262144, **N/2=131072 Float32**, то есть до FFT **1 048 576 байт**, power/Y по **524 288 байт** каждый. Полные Y для Tag0–3 уже были сравнимы по 131072/131072, поэтому **[EBP-14]=4096 не может автоматически переопределять размер спектра**. Указатель ECX не обязательно сохраняется при исполнении: инструкция по 14AA может его перезаписать, в отличие от читаемых локалов. `Storage+34` (исходное кольцо Float32) и `[EBP-2C]` (рабочий буфер) по природе **разные объекты**; различие адресов `7E620010` и `7E510010` не делает первый «невалидным». Нужны bounds/region/mask. Не допускать RAW-byte dump в облако.

## Что разрешено следующему локальному агенту

**Только read-only**: получить актуальные регистры/состояние, снять маленькие сырые блоки параметров `EBX..EBX+0x3B` (60 байт), `Storage..Storage+0x37` (56 байт), `[EBP-0x30..EBP]` (48 байт); Storage указатель взять из read_memory по EBP-4. Декодировать **локальным детерминированным Python struct** `<I` и `<f` со строгими длинами/границами, не текстом ИИ. Проверить `EBX+18`, `Storage+10/+14/+18/+34`, FRange и region mapping для ring/work. Размеры и указатели не брать из старой Win32 сессии.

**Никаких single-shot breakpoints, resume/step, памяти/регистров/оригинального EXE edits до отдельной проверки и одобрения оператора**. Сначала вывести поля с offsets, raw_hex, decoded_value, ambiguity; ошибки вместо догадок. После успешной проверки можно подготовить локальный state-machine, который проходит эти 6 адресов в рамках **одного EBP/EBX/TID/RAW end/N/Fs/Mode** и сохраняет массивы локально, по умолчанию только агрегаты/SHA к модели. Использовать существующий Stage111Z31R verifier и проверенные FFT/FRange/Tag0–3, не переписывать математические модули.

## Статус

**GigaCode MCP ↔ x32dbg подключение: наблюдалось.** Report correctness: **FAIL**. Original A/B complete, original same BIN-window, FIR/IQ, Y 1:1: **не доказано из obmen**. Дальше нужна read-only проверка сырых байтов, не F9. Оригинальные EXE/IDP/PAS/RAW/BIN и крупные дампы хранить только локально, не коммитить.

## Дополнительное свидетельство оператора — отрисовка ещё не закончилась

Пользователь уточнил: **x32dbg остановил оригинальную MVKView на EIP=007D14AA сразу после перехода на страницу спектра, когда логарифмическая шкала ещё не успела прогрузиться**. Это ожидаемо для точки *внутри GetSpectrum до FFT/постобработки*: вычисления/отрисовка не обязаны закончиться к моменту INT3. Не трактовать незаполненную шкалу как сбой алгоритма, неверную функцию или подтверждение конкретного SpectrumMode. Режим определять строго по `DWORD[EBX+0x18]`, код огибающей — `DWORD[EBX+0x08]`, сохранённому RAW/стопу и меню после завершения вычислений; `EBX+0x0C` не является проверенным SpectrumMode. Приостановку **сохранить**, F9 до диагностики/санкционированного захвата не выполнять. Для отдельного UI/pixel-паритета позже потребуется дать исходному GUI завершить GetSpectrum и отрисовку; это отдельная процедура, не pre-FFT capture.
