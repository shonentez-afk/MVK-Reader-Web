# MVKView 1.0.47 — исходный численный GetSignal/GetSpectrum: порядок накопления Float64

**23.11.2026. Ветка research/stage111-mvkview-desktop-20261029.** Основная ветка main не изменяется. Не публиковать оригинальные PAS/DFM, mvkview.idp, SQLite, BIN/TSXML, VALUES/TABLE и PCAP.

## Что ещё было неправильно после восстановления приёма

Исходный _Unit115.pas на 007D0D9F..007D0DAD (GetSignal с фильтром) и 007D0DFB..007D0E03 (GetSignal без фильтра) делает: `fld Single; fmul st,st(0); fadd qword [SUM]; fstp qword [SUM]` в **каждом отсчёте**. Это последовательный обход Float32 входа, хранение суммы квадратов в Float64 **после каждого отсчёта**, затем `Sqrt(sum/N)` и Single store `Params.OutputMean`. Не одновременно-агрегирующая, не попарная сумма.

В исходном `mvk_compatible/core/signal_idr_candidate.py` использовался NumPy `np.sum(float64 squares)` с возможной парной редукцией. Математически это та же сумма, но порядок округлений другой; возможен другой последний бит Float64 и иногда Float32 RMS, особенно на длинных окнах.

Исходный `GetSpectrum` (_Unit115.pas 007D1807..007D1810) использует такую же последовательную **Float64 qword store** для суммирования всех полных power-бинов от `first` до `last`; 5-элементная peak-weighted окрестность отдельно сохраняется в **Float32**. Старый код этого участка уже был верен, но делал медленный Python `for`, что могло задерживать Qt на длинной FFT.

## Исправления основного расчётного кода (НЕ новая реализация приёмника)

- `signal_idr_candidate.py`: добавлен `source_stepwise_signal_power_f64(samples)`, `np.cumsum(np.square(samples.astype(float64)),dtype=float64)[-1]` с теми же последовательными Float64-store границами, что у оригинала, отказ при пустых/NaN/Inf. `unfiltered_getsignal` теперь использует эту функцию для AC/DC RMS. Порядок GetSignal[n-1-i], исходная реализация Float32 mean/DC и FRange не меняются.
- `spectrum_metrics_idr_candidate.py`: заменён медленный Python `for` по полному FFT POWER на эквивалентное по разрядности/порядку `np.cumsum` в Float64. Целиком сохраняется исходный summary `DELPHI_STEPWISE_F64_STORED`, first/last-bin, strict-first peak, +/-2 weighted Float32, режимы Y, низкие бины, Hann, FFT и FRange — всё без изменений.
- `test_mode2_source_stepwise_getsignal_getspectrum_one_window.py`: новый синтетический контракт сравнивает NumPy accumulate с НЕЗАВИСИМЫМ скалярным Python циклом 262144 отсчётов, демонстрирует отличие от попарной суммы, проверяет один и тот же SHA-backed Float32 вход для NoDC GetSignal и pre-Hann GetSpectrum (без повторного удаления DC), реверс GetSignal, совпадающий full power, целостность исходного входа, NaN/Inf/пустые окна и 4 длины.

- Аналогично сравнение N1024/4096/8192/65536 подтвердило отличия сумм накопления при совпадающем Float32 RMS на данных окнах.

## Границы достоверности

Исправленная последовательность Float64 соответствует семантике **исходного дизассемблированного кода** при предположении обычного x87 CW с сохранением qword. Полный точный Win32 x87 Sqrt/Delphi Float32, FFT twiddle/rounding, Hann Cos и весь спектр все ещё не сравнивались на ТОЙ ЖЕ исходной RAW-последовательности с оригинальным работающим EXE. Ни одна source-кандидат метка не повышена до подтверждённого аппаратного паритета. На исходном BIN InternalChannelGain=510.6, а source-live FRange=1 — не смешивать.

Предыдущий commit 17c294d / CI #45093286454 на момент подготовки документа: Linux Core и Go PASS, Windows Core/Qt и QPA PASS, автономный EXE на проверке; обязательно сверять ПОСЛЕ сборки. Новый SHA/CI этого пакета сверять отдельно. Пайплайн IP → Измерить → Task2 → приём → расчёт → WriteData/Values/Table → Stop не дублируется, сетевые команды и приватные файлы не меняются.
