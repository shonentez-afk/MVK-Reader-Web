# Stage 100 / Native R4 — проверка сетевого сеанса, команды частоты, калибровки и записи

**Дата:** 2026-10-29. **Статус:** реализовано и протестировано офлайн; не проверено на реальном Live-соединении. Стабильная MVK Reader Web v0.3.40 не изменена. **Рабочий порт — исключительно TCP/10230.** Документ Modbus/502 используется лишь как карта значений регистров, а не как обязательный транспорт.

## 1. Источники и принцип восстановления

- Оригинальные IDR `_Unit125.pas` (сетевой поток `TMVKThread.Execute`, задания 0, 2, 3–5, команды, ошибки и запись) и `_Unit115.pas` (`TMvkChannelStorage.AllocBufferChunk` и `ProcessBufferChunk`). Исходные IDR не публикуются.
- Два оригинальных офлайн-захвата PCAPNG, не синхронизированные с MVK43 BIN+VALUES; не использовать эти сессии для временной корреляции.
- Действующее собственное ядро Native R3, **не** `mvk_tcp_reader_v2`.
- Четыре предоставленных оригинальных TSXML. Схема проверена по ним, без опубликования исходных метаданных.

## 2. Новый результат — исходящий формат установки частоты подтверждён в PCAPNG

В захвате «83 спектр» присутствуют ровно **два TCP-сегмента клиента с полезной нагрузкой, 4 и 32 байта**. После сортировки TCP sequence они образуют 36-байтный кадр:

`<9I LE`:

1. `0xFF800C0D` — адресованный блок;
2. `0x00000024` — длина 36;
3–6. четыре нулевых служебных поля;
7. `1` — число блоков;
8. `0x0002000E` — 2 регистра по адресу 0x000E;
9. `0x00010000` — значение частоты 65 536 Гц.

Результат **побайтно совпал** с чистой функцией `rate_message_preview(65536)`. Сопоставление с IDR: `0x00809364` (формирует команду с адресом 0x000E), `0x0080937C` (32-байтная шапка + 4 байта данных), `0x00807F45–0x00807F52` (отправка значения). В `1111` исходящие прикладные данные не наблюдались. **Не означает**, что команда должна отправляться сразу после подключения или что все ревизии прибора используют одинаковый сценарий.

## 3. Подтверждённый сетевой цикл оригинала

| Факт | Опорные адреса IDR | Степень подтверждения |
|---|---|---|
| Порт 10230; тайм-аут подключения 1 с, чтения 5 с | 0x00807C12, 0x00807C24, 0x00807C34 | Прямой IDR |
| После Connect переход к чтению, без безусловной команды запуска | 0x00807CA7, 0x00807CE0, 0x00807F78 | Прямой IDR, но не доказательство совместимости всех приборов |
| Служебный ID (видели длину 264), регистровые снимки; первый непустой блок переводит Stage 0→1 | 0x00808060, 0x00808455, 0x00808617 | IDR + реальный PCAP |
| Task=0 после готовности завершает однократное чтение; Task=2 продолжает приём | 0x00808724, 0x00808786, 0x0080884C | Прямой IDR |
| Положительный ответ 0x00010FF0, отказ 0x00010FFF | 0x0080804F–0x008080AC | Прямой IDR; реальные ACK/DENIED в двух захватах не наблюдались |
| При отказе, закрытии соединения, timeout исходник имеет разные исключения; Stage 2 может не пометить ошибку | 0x00808871–0x0080897E, 0x008092BD | Прямой IDR; потенциальный GUI-дефект не тиражируем |
| Задания записи конфигурации 3–5 включают запись Flash и перезагрузку | 0x00807D00–0x00807E4A | Прямой IDR, **не реализовано** в собственном read-only клиенте |

`reconnect_preview.py` без сети воспроизводит арифметику оригинального ожидания: начальное PauseValue=25; при сбое Task=2 число ожиданий по 10 мс — Round(PauseValue)+1; затем умножение PauseValue на sqrt(2), пока оно меньше 801. Ветвь постановки команды частоты зависит от порога 26. Это **статическая интерпретация x87**, а не измеренный тайминг реальных переподключений; исполняемого автоподключения в R4 нет.

## 4. Новый результат — доказан порядок пересчёта ADC перед BIN

В `_Unit115.pas:0x007D1B08–0x007D1B5E` `AllocBufferChunk` выдаёт адрес `PAdcFloatData`. В `_Unit125.pas:0x008081F3–0x0080822B` этот адрес передаётся как память `TRecordMemoryStream` и туда читается сырой сетевой payload. Затем `_Unit115.pas:0x007D23B7–0x007D23E1` при формате `Single` и `ApplyRange=True` **умножает каждый отсчёт in place на `TMvkChannelStorage.FRange`**. Наконец `_Unit125.pas:0x008082C3–0x008082DE` записывает именно эту память в файл.

Следовательно, исходный экспорт BIN содержал уже откалиброванные `float32`; применять к готовому BIN gain повторно **нельзя**. Ранее это подтверждалось лишь численно на парах архивов; теперь опирается на точную цепочку команд PC-IDR. В `recording_r4.py` добавлена отдельная безопасная проверенная синтетическими тестами реализация `raw_float32 * verified_FRange → float32_LE`.

**Ограничение:** отдельные битовые результаты float32 при x87-округлении ещё не сверены на идентичной полной PCAP/BIN сессии. Коэффициент для записи необходимо брать из той же конфигурации прибора, не заимствовать из другого сеанса.

## 5. Восстановление файлов BIN и TSXML

- `CalibratedBinSink` принимает только один явно выбранный АЦП, проверенную частоту и положительный конечный FRange; по индексу АЦП контролирует непрерывность блоков по 256 отсчётов.
- Сначала пишет `.bin.partial`; лишь при безошибочном завершении создаёт `.bin.tsxml` и переименовывает `.partial` в `.bin`. Не перезаписывает существующий файл. При ошибке оставляет `.partial` и **не** объявляет BIN корректным.
- `generate_tsxml` создаёт windows-1251, `MainRoot`, DateTime / Culture en-US, From/To ms, FrequencyPerChannel, DataFileName, ChannelNumber, ChannelFrequency, Units, `Single`, DataLength, DataOffset, InternalChannelGain.
- **4/4 оригинальных TSXML** совпали по структуре, сравнимым метаданным и длительности при реконструкции. Это проверка формата, не доказательство эквивалентности всей GUI-функции записи оригинала.
- VALUES: `NativeSession` фиксирует событие адреса `0x3100`; CSV-генератор с локальным временем, выбранными `GetValueText` полями и заголовками Stage77 **ещё не подключён**. TABLE (разовая кнопка в GUI), тахометрические BIN, архивные процедуры и аварийное завершение нескольких файлов тоже остаются открытыми.

## 6. Реальные тесты Native R4

| Показатель | Захват 83 | Захват 1111 |
|---|---:|---:|
| AUX4700 обновлений / наборов восьми каналов | **122** | **170** |
| Кадров АЦП | 125 440 | 173 469 |
| Кадров тахометров | 31 360 | 43 368 |
| Меток VALUES по адресу 0x3100 | 122 | 170 |
| Служебный ID, 264 байта | Да | Нет, начало захвата в середине сессии |
| Полный образ 16384 регистров, кадр 32800 байт | Да | Нет, начало захвата в середине сессии |
| Потерянные промежутки в отсортированном TCP | 0 | 0 |
| Неоднозначные байты в повторных сегментах | 3 | 2 |
| Неполных байтов последнего кадра | 988 | 0 |

Старые неоднозначные байты остаются в 160-байтных вспомогательных сообщениях. Прогон потребовал явного выбора архивной политики `preserve_assembled` (в обычном режиме она запрещена), конфликт записан в отчёт и не был переписан молча. Поля AUX4700 в R3 ранее прошли отдельную побайтную проверку всех 144+status для каждого канала.

## 7. Тесты, исходники, безопасность

- **27/27** автономных тестов `test_r4.py`, `test_recording_r4.py`, `test_reconnect_preview.py` — PASS.
- **32/32** отдельных адресных опор IDR в `_Unit125.pas` — PASS (`r4_idr_check.py`).
- **4/4** исходных TSXML совпали по проверяемой структуре, метаданным и длительности (`tsxml_schema_verify.py`).
- **1/1** наблюдавшийся исходящий 36-байтный блок совпал побайтно с реконструированным rate-командным форматом (`outbound_verify.py`); в другой записи исходящих payload не было.
- Никаких соединений с приборами, отправок, FC16 или изменённого кода v0.3.40. Исходные IDR/PCAPNG/BIN/TSXML не загружать в GitHub.

**Что ещё нельзя объявить восстановленным:** полноценное живое подключение с подтверждённым переподключением, обработка статусов контроля/отказов всех ревизий, точный start/stop и исключения записи файлов по всем кнопкам, полный VALUES/TABLE, исходные цифровые фильтры DSP. Для Live потребуется отдельный стенд и проверка без управляющих команд, затем согласованный тест установки частоты.
