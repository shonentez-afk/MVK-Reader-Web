17.11.2026. Исследовательская ветка.

## Сверка по трём источникам

Локальные `mvkview.idp`, `Projects.7z`, `mvk_idr(1).sqlite` открыты совместно: заголовок IDP и SHA совпали с SQLite, `quick_check(1)=ok`, четыре извлечённых PAS/DFM совпали по размерам и SHA. В `TMVKThread.Execute 00807A98` (IDP и `_Unit125.pas`, `sqlite.functions/calls`) соединение Indy TCP повторяется после EIdConnClosedGracefully / EIdReadTimeout / EIdConnectTimeout. В Source Task2 `008089A3..00808B0E` ожидание повторения 260/360/510/720 мс до 8020 мс. Исходная `SetRate 00809400` и очередь `QueueCommand 00809330` — отдельный путь, а не обязательное условие TCP retry.

## Восстановлено Go/Core/Qt

- Дополнительное явно разрешённое переподключение доступно даже **без** отдельного разрешения аппаратной команды SetRate. Чекбокс по умолчанию снят.
- Повторное TCP-подключение требует `-source-task2-reconnect=true`, `-source-task2-reconnect-approved=true`, операторского `-approve`, локального `-stop-file`, статусного `-live-status` и установленного лимита RAW. Нет скрытого подключения или поиска прибора.
- Go не создаёт аппаратную очередь и не читает команды изменения частоты из stdin, если SetRate запрещена; при пассивном повторном подключении проверяет 5-секундное отсутствие потока, откатывает состояние фреймера/регистров на новый сокет.
- Go сохраняет каждый TCP-сеанс отдельным SHA256 RAW. Python Core запрещает выдавать конкатенацию после нескольких TCP-соединений за один исходный BIN. В Qt явно указывается, будет ли аппаратная SetRate.
- Добавлены автономные проверки настоящих loopback TCP сокетов без исходящей команды, независимого подтверждения в Core и состояния чекбоксов Qt.
- Исходные Pascal/DFM, IDP, SQLite, RAW, PCAP и IP оборудования не публикуются в GitHub.

## Ограничения

Точный результат исходного Delphi DSP/FFT/WriteValues и работа на физическом приборе всё ещё НЕ доказаны; пассивный retry воспроизводит сетевой жизненный цикл, но не исходный обмен SetRate. `original_delphi_compatibility_verified=false` остаётся.
