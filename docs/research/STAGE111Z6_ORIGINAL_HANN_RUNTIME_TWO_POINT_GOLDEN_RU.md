# Stage111Z.6 — два оригинальных runtime Hann Float32 эталона из x32dbg
Дата: 30.10.2026. Ветка: `research/stage111-mvkview-desktop-20261029`.
Назначение: продолжение автономной Windows MVKView Compatible; не возвращаться к Web v0.3.40.

## 1. Происхождение результатов

Оператор прочитал два 32-битных значения из памяти РАБОТАЮЩЕЙ оригинальной 32-bit MVKView в x32dbg, когда инициализирован Hann и открыт спектр. Это пользовательские результаты, без независимого повторного считывания этой сессии средствами CI. В GitHub не загружены оригинальные EXE/IDP/PAS/DFM/BIN/RAW/PCAPNG и реальные сигналы прибора.

Таблица оригинального Hann: `0x0096DA48` в BSS, 262144 элемента IEEE754 Single. Формула адреса — `base + 4 * index`.

| index | x32dbg expression | Original Win32 dword bits | Source-derived GCC x87 CW0x1372 | Existing NumPy candidate |
|---:|---|---|---|---|
| 1 | `dword:[96DA4C]` | `2F80EF9C` | `2F80EF9C` | `2F80EF9D` |
| 5 | `dword:[96DA5C]` | `31C97664` | `31C97664` | `31C97663` |

**Объективная проверка:** 2/2 оригинальных значения совпадают с source-derived native x87 побитово; NumPy различается на один Float32 ULP в каждом случае. Статус — **OPERATOR-REPORTED ORIGINAL RUNTIME 2-POINT GOLDEN**, а не full-table-verified.

## 2. Что изменилось в статусе модели

Stage111Z.5 обнаружил четыре потенциальных несовпадения native-vs-NumPy на index `1,5,262139,262143` из полного 262144-элементного массива. Теперь первые два доказаны наблюдением оригинала; последние два всё ещё **не измерены** в оригинальном Windows-процессе. Для FFT N<262144 и power-of-two original stride=262144/N, эти нечётные индексы не используются. Для максимального N=262144 хотя бы два коэффициента текущего NumPy-кандидата действительно отличаются от проверенного оригинала.

Из двух значений нельзя достоверно заключить, что вся таблица идентична GCC/x87: функция `FCOS`, FPU control word во время инициализации и операционные округления могут иметь пограничные особенности. Не заменять всю таблицу, не объявлять общий Delphi FFT / GetSpectrum parity и не менять Qt-ось из-за всего двух наблюдений.

## 3. Регрессионный код

Добавлен тест `mvk_compatible/tests/test_stage111z6_original_hann_runtime_golden.py`: хранит только две пары (index, битовое значение), проверяет native x87 `--summary` на них, допускает исправление NumPy-кандидата в будущем, и отмечает что меньшие размеры FFT не выбирают нечётные крайние индексы. Тест использует полностью синтетический локально собранный GCC x87-пробник и **не выполняет оригинальный EXE**.

Предыдущий Stage111Z.5 программный HEAD `9772e8a4f7dc8e84e217bf79d1a76a0cd0c9008b`: [Linux #177](https://circleci.com/gh/shonentez-afk/MVK-Reader-Web/177) SUCCESS, [Windows Core+Qt #178](https://circleci.com/gh/shonentez-afk/MVK-Reader-Web/178) SUCCESS, [Windows Preview EXE #179](https://circleci.com/gh/shonentez-afk/MVK-Reader-Web/179) SUCCESS. ## 4. Следующие два оригинальных runtime чтения (Stage111Z.6 completion)

В x32dbg с остановленным процессом оригинальной MVKView, после инициализации таблицы, прочитать **только**:

```text
dword:[A6DA34]  // index = 262139
dword:[A6DA44]  // index = 262143
```

Ожидания модели GNU x87 (гипотеза, НЕ измеренное значение оригинала): `31C97664` и `2F80EF9C` соответственно. Если они совпадут, все четыре известные точки отличия NumPy на данном CPU будут покрыты подлинными user-reported golden.

После этого рассмотреть строго минимальную детерминированную коррекцию Hann для **N=262144** и автоматические тесты, сохраняя отдельную ветку без сетевого сервера; не вводить эмпирическую поправку на других размерах FFT.

Стабильный `main`, Web v0.3.40, приватные файлы оригинала и реальный прибор не изменять.
