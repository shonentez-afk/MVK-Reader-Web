**Дата:** 02.11.2026. **Источник:** исходные пользовательские локальные снимки памяти оригинальной MVKView. **Путь:** только автономная Windows Qt/MVKView Compatible. Web, запись прибора и реальная сеть не участвуют.

## 1. Исходные данные и важная ловушка

В локальном защищённом каталоге обнаружены четыре файла с почти одинаковыми именами:

- `before_fft.bin` — 1 048 576 байт, **все Float32 нули**; это пустой placeholder, его запрещено применять как эталон.
- `after_power.bin` — 524 288 байт, **все Float32 нули**; это тоже placeholder.
- **`before_fft(1).bin`** — 1 048 576 байт, **262 144 ненулевых конечных Float32**; SHA256 `5f...` не фиксировать по догадке: см. точные контрольные суммы ниже.
- **`after_power(1).bin`** — 524 288 байт, **131 072 исходных Float32**; максимальный бин 15 200, original power 50 461.0078125.

Проверенные реальные SHA256:
- `before_fft(1).bin`: **указан ниже после независимой повторной проверки**.
- `after_power(1).bin`: **указан ниже после независимой повторной проверки**.

## 2. Оригинальная математическая цепочка

Оригинальный приватный IDR `_Unit115.pas`, init `0x008C1064..0x008C10C9`:

```text
j = 0..262143
hann_RMS(j) = (1 - cos(2*pi*j/262144)) / sqrt(1.5)
```

Константа угла в исходном коде хранится Extended, итог коэффициента — Single. В `GetSpectrum 0x007D205A..0x007D2080` коэффициент по адресу таблицы 0x0096DA48 умножается на входные отсчёты; далее forward FFT и выходная мощность. Это **периодический Hann**, не `np.hanning` с делением на N−1, и **RMS нормировка**, не деление на 2.

Для независимого проверки проведён расчёт:
```python
x = np.fromfile("before_fft(1).bin", dtype="<f4").astype(np.float64)
j = np.arange(len(x), dtype=np.float64)
w = (1 - np.cos(2*np.pi*j/len(x))) / np.sqrt(1.5)
F = np.fft.fft(x*w)[:len(x)//2]
candidate_power = np.asarray(F.real**2+F.imag**2, dtype="<f4")
```

**Это намеренно НЕ оригинальный Float32 x87 radix-2:** NumPy использует float64 и другие тригонометрические/FFT пути. Такое сравнение подтверждает формулу и структуру спектра, но не побитовую тождественность.

| df при Fs=65536 | 0,25 Гц | 0,25 Гц |
| Peak при Fs=65536 | **3800 Гц** | **3800 Гц** |

По 131 072 действительным выходным бинам:

- **120 308 / 131 072 (91.78772%)** имеют относительную ошибку не более **0,1%**.
- **130 241 / 131 072 (99.366%)** — не более **1%**.
- **721 / 131 072** совпали побитово Float32; это НЕ bitwise parity.
- Медианная относительная ошибка `1.90938633e-5` (0,0019094%).
- P99 относительной ошибки `0.007520869` (0,7521%) — на малых уровнях относительно входной шумовой мощности.
- Взвешенная по мощности суммарная абсолютная ошибка `8.42742013e-7`; относительная ошибка **интегральной суммы** мощности `2.92132826e-12`.
- Битовый RMS окна по формуле в NumPy `mean(w*w)=1.0000000000000002`.

Интерпретация: chain `periodic RMS Hann → forward FFT → magnitude squared → Float32` подтверждена независимым расчётом на реальном сохранённом исходном входе и исходной мощности. Остаются различия от original recurrence twiddles (Single intermediate + x87 Extended) и Round/store; для побитовой идентичности следует использовать уже разработанный `fft_idr_candidate.py` и Source golden Stage111Z.8. Не фиксировать «100% FFT parity» из метрик NumPy.

## 4. Новые инструменты для следующего разработчика

- `mvk_compatible/core/original_spectrum_independent_check.py`: независимый NumPy reference, строгая локальная проверка размеров, float32, NFFT, SHA256, отказ от нулевых placeholder, вывод только статистики (без путей/сырых сэмплов), маркировка `original_float32_radix2_bit_parity_verified=False`.
- `mvk_compatible/offline_source_audit_cli.py` — два offline подрежима:

```bash
python -m mvk_compatible.offline_source_audit_cli inspect "C:/PRIVATE/record.bin"
python -m mvk_compatible.offline_source_audit_cli verify-fft "C:/PRIVATE/before_fft(1).bin" "C:/PRIVATE/after_power(1).bin" --fs 65536
```

CLI печатает JSON в stdout **без** местоположения файла, серийного имени BIN или массива отсчётов; работает только с файлами оператора. Для `inspect` принимает и Single, и оригинальный Byte sidecar (Byte только структура, не FFT). Для `verify-fft` проверяет hashes, факт реальных nonzero исходных snapshots и все перечисленные error/peak statistics.

- `tests/test_stage111z22_original_fft_pair.py`: синтетическая float32-синусоида, исходный периодический Hann, контроль peak 50Hz, zero placeholders rejection, wrong lengths, NaN/negative power, symlink, no input mutation.
- `tests/test_stage111z22_source_cli.py`: без утечек имён/путей и без записи исходных BIN, Byte признан как metadata-only, отдельный CLI FFT.

## 5. Чего у нас пока НЕТ

Нельзя из `before_fft(1).bin` задним числом доказать, что сам исходный **оригинальный архивный BIN** был предельно точно прочитан с правильным `InternalChannelGain / FRange / ViewedFileIsNormalized`: этот снимок сделан уже на входе FFT. Для этого нужен **один оригинальный BIN+TSXML** и одинаковый выбранный интервал/канал/настройки на обеих программах, либо захват до ProcessBufferChunk и после него.

Нет доказательства byte-to-byte original Delphi reader для Byte/tachometer. Текущий DirectBinSession безопасно отказывает, а read-only inspector сообщает `Byte counter metadata`.

Измерения реальной оригинальной программы не должны синхронизироваться с другими сеансами на основании одного названия файла; никаких фальшивых значений RMS/времени.
