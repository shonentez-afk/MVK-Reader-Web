# Stage 13 — отбор качественных каналов МВК01 по бинарным файлам (26.10.2026)

## Решение и входящие материалы
Пользователь планирует **27.10.2026** предоставить бинарные файлы штатной программы с **8 АЦП прибора №83 и 8 АЦП №84**. Возможна также таблица числовых измерений из отдельной от спектра страницы MVKView. Время данных не обязано совпадать со временем наших PCAPNG; нельзя сравнивать амплитуды как одновременные при разном режиме работы.

**Задача:** сначала беспристрастно оценить качество **всех 16 каналов**, выделить пригодные для независимого FFT/СКЗ и сравнения с MVKView, избежать повторных полевых замеров на заведомо дефектных датчиках. Не выбирать канал только по красоте спектра; реальная широкополосная вибрация, удары или резонансы не равны браку. Не подгонять алгоритмы под выбранный «красивый» сигнал.

## Три независимых класса пригодности
- A — пригоден для верификации измерительного ядра: целостность потока, физически правдоподобный канал, стабильная калибровка, достаточно стационарный фрагмент, нет неисправностей входа.
- B — пригоден условно: указать проблемный интервал, диапазон частот и причину (помеха, изменение режима, высокий шум, отсутствие метаданных). Такие каналы могут использоваться для проверки устойчивости.
- C — исключить из основной *эталонной* выборки: обрыв датчика, перегрузка АЦП, постоянное насыщение/плоский сигнал, повреждённые отсчёты, потеря синхронизации. Сохранить в тестовой коллекции диагностики, не удалять.

Присваивать отдельно status: PASS/WARN/FAIL/UNKNOWN, и use_class A/B/C; UNKNOWN при недостаточном материале, а не автоматически FAIL.

## Методика оценки (каждый АЦП)
**Слой 0 — подлинность файла:** тип/версия/метаданные бинарного контейнера, device+ADC id, fs, duration, units, sens/gain и точная связь с экспортом таблицы. Если формат не расшифрован — сначала reverse engineering на уровне структуры, без домыслов.
**Слой 1 — транспорт и аппаратный статус:** контроль счетчиков ADC по 256, gaps/overlap/duplicate/wrap, 65536 Hz, количество отсчётов, неполные кадры, валидность VAST_MVK, значения AUX4700 status. Для известной конфигурации №84 АЦП7/8 — bit10 (0x400) и сообщение MVKView «Обрыв кабеля»; №83 АЦП1 bit11 (0x800), АЦП5 bit10 (0x400). Не считать эти состояния неизменными в будущих файлах.
**Слой 2 — качество временного сигнала:** finite fraction, min/max, DC, drift, RMS/median RMS по окнам 0.25/1/2 s, peak/crest, kurtosis, skewness, доля exact-duplicate/flatline, обрезания возле физического/ADC max (предел уточнить по документации), доля повторяющихся плато, резких одиночных переходов (MAD производной), джиттер и временные разрывы. Абсолютные пороги RMS и crest не задавать до контекста машины.
**Слой 3 — спектр:** Welch PSD (Hann, 50% overlap), независимый FFT (RMS and peak), high-pass и integration sensitivity, спектральные пики/полосы 0–100/200/1000/3000 Hz, 50 Hz и гармоники отдельно как **подозрение** на наводку, не автоматический дефект. Spectral flatness, line-to-background, broad-band noise floor, tonal energy ratio, stationarity across segments; coherence между каналами/периодами только когда сигналы **синхронизированы**.
**Слой 4 — устойчивость и повторяемость:** сравнить окна одного файла; сравнить отдельные временные замеры только при сопоставимых оборотах/нагрузке/режиме машины; таблицу MVKView связать по time/channel/units/filter. Проверить выбросы АЦП2 №83 и не полагаться на нулевой AUX160 №84.
**Слой 5 — suitability for test:** A для сравнения FFT, B для robustness и diagnostics, C для negative tests. Выбирать >=2 A-канала с каждого прибора при наличии; если их нет, не заставлять это число.

## Результат — 16×1 таблица и подробные карточки
`channel_quality_matrix.csv` c device/adc/source file SHA256/status/use_class/reasons/fs/duration/valid_samples/gaps/diagnostic_bitmask/rms_m_s2/crest/kurtosis/clipping_fraction/flat_fraction/spike_rate/stationarity_index/main_peak_hz/50hz_noise_indicator/calibration_status.
`quality_ADC{n}.json` — метрики по временным окнам, метаданные и обоснование вердикта.
`quality_summary_ru.md` — рейтинг кандидатов для эталонного сравнения и запретных, аргументы и требуемые подтверждения.
`reference_pairs.csv` — строгая привязка двоичный файл ↔ таблица MVKView ↔ спектр (identical acquisition if possible; otherwise method-only).
Нулевые/ошибочные каналы сохранять в наборе регрессионных тестов для проверки обнаружения неисправностей.

## Контроль порогов
Ни kurtosis>3, ни большой crest-factor, ни сильная линия 50 Hz сами по себе не означают брак: ударный подшипник/машина/режим может создавать такие признаки. Пороговые правила первоначально экспериментальные, фиксировать версии и объяснения; приоритет отдать достоверным аппаратным флагам и целостности отсчётов. Для 50Hz проверить известную частоту вращения, кратность и одновременное появление во многих каналах.

## Заимствования из открытых реализаций
- ObsPy `Stream.get_gaps()` и сохранение структуры разрывов/overlap, вместо скрытого заполнения нулями: https://github.com/obspy/obspy/blob/master/obspy/core/stream.py
- SciPy `signal.welch`, `spectrogram`, `coherence` — явные window/nperseg/noverlap/scaling и сравнение спектров: https://github.com/scipy/scipy/blob/main/scipy/signal/_spectral_py.py
- Событийные исследования (spike/outlier) проверять одновременно во временной и частотной областях; формальный correlation/coherence не доказывает электрическую природу наводки.
- QCoDeS metadata/run-id и Frictionless отчёт ошибок из Stage13 Evidence Bundle: `docs/STAGE13_FIELD_EVIDENCE_BUNDLE_SPEC_20261026_RU.md`

## Последовательность работ после поступления данных
1. Инвентаризация и SHA256 всех бинарных файлов; не изменять оригиналы.
2. Декодировать формат, извлечь 16 каналов и калибровку, проверить полноту.
3. Стандартизировать единицы и вычислить метрики/FFT/PSD оконными методами.
4. Проверить статусы и причины аномалий, строить верифицируемые графики для спорных каналов.
5. Таблица качества A/B/C с confidence and evidence; выбрать каналы эталонного сравнения.
6. Сопоставить таблицы и спектры MVKView, не смешивая неодновременные замеры.
7. Версионированный ZIP Evidence Bundle на прибор и общий cross-device отчет; source SHA256 + software versions + расчётные настройки + CSV/JSON metrics.
8. Отдельные тестовые наборы good channels и corrupted/noisy channels; использовать для regression ядра Stage13.
